# Configured Codex startup discovery

`daemon --config FILE [--until-idle]` accepts exactly one source selection. The existing `claude_main` selection keeps its single-location behavior. A Codex selection explicitly names a home:

```json
{"codex_home":{"home":"/absolute/disposable-codex-home","machine":"synthetic-machine","host":"synthetic-host"}}
```

Optional `rollouts`, `catalog` and `history` paths default to `sessions`, `state_5.sqlite` and `history.jsonl`. Relative paths, including `threads.rollout_path` values, resolve against the configured home. Parent traversal, paths outside that home and source symlinks refuse. No default Codex home is opened. Startup reads sources without provider repair and registers no watcher.

Store enumerates `rollout-*.jsonl` independently of thread registration. It separately opens the configured SQLite catalog read-only, pins a read transaction and admits its `threads(id, rollout_path)` rows. A missing or malformed catalog does not prevent independently enumerated rollouts from being retained. Each readable admitted rollout becomes an immutable snapshot through the existing capture/import owner and keyed Codex interpreter. Changed bytes become another retained snapshot; this path does not claim observed revision lineage. Ordinary `origin:codex` discovery, `tool_calls where session:ID`, and returned operation references use the shared CLI and MCP readers. Unknown general Session and source coverage stays unknown.

`status.acquisition` describes this startup only. `accessible_empty` means a completed accessible traversal or empty file; `unavailable` carries a reason and `entries: null`. It never establishes a zero source population. A failed traversal may still have acquired an explicitly reported prefix. `retained_count` and `refused_count` account for successful and failed source capture attempts, independently of content deduplication. `retained` samples at most 32 input IDs and `refused` samples at most 4 failures, with explicit omitted counts; this presentation never limits completed acquisition. Availability counts name their units: rollout paths, thread rows or retained history inputs. An empty history input still counts as one retained input and reports `accessible_empty` for its bytes. Paths larger than 1024 encoded bytes are omitted with a BLAKE3 `path_key` of the original path bytes; truncated reasons are marked. Catalog rows, filesystem enumeration and source snapshots are separate observations, not one atomic provider snapshot. Removing an original rollout changes current acquisition evidence while retained operation citations remain readable.

`codex-prompt-history` owns retained `history.jsonl` bytes using the existing input/observation/extent schema. It has no conversation parser or canonical row settlement certificate. The sources crate alone projects complete supported JSONL records with nonempty `session_id` and string `text`; timestamps and prompt contents do not become Messages. Store supplies verified retained bytes and original machine/host/path/acquisition-time provenance. The engine exposes exact record byte ranges and BLAKE3 hashes under `pending_references` on status and queries. Reference counts describe supported prompt-record observations in retained snapshots, never distinct conversations or Messages. Public replies carry bounded reference and snapshot samples, observed counts, omitted counts and explicit scan/presentation completeness. A partial scan reports unknown totals and its observed prefix. Exact failed conversation reads filter by the requested Session before presenting reference details. Optional arrays yield to primary query rows at CLI/MCP presentation limits. No conversation Session row is manufactured for a prompt-only reference. A bounded read of that reference returns an unavailable conversation result with its pending source evidence, never a completed empty conversation or invented assistant response. Malformed records and incomplete tails stay explicitly counted.

When independently acquired conversation evidence publishes the same opaque provider Session identity, the reference reports `conversation_evidence`. Its prompt provenance remains separate and conversation coverage remains unknown. Duplicate prompt records are source observations, not additional sessions or conversational Messages. A regular restart without source configuration still exposes retained reference evidence. Failed provider acquisition does not erase earlier snapshots.

Admission bounds are 512 visited directory entries, depth 8, 512 catalog rows and 512 combined rollout paths. Individual files and the catalog are at most 16 MiB; one startup captures at most 32 MiB. Prompt snapshots admit 1 MiB and 4096 references; public projection examines a prefix of at most 512 retained prompt snapshots, 4 MiB total prompt bytes and five seconds of work. Its reference sample admits 8 KiB and snapshot sample 4 KiB, with explicit omitted/unknown counts. Startup acquisition metadata samples fit 16 KiB independently of completed capture. The existing rollout parser and operation publication/read bounds also apply. Admission failures refuse or explicitly account for partial acquisition, never certify an empty population.

`scripts/check-codex-discovery.py --binary PATH --output NEW_DIR` exercises an exact packaged binary through ordinary CLI and actual SDK MCP processes. The declared `configured_codex_demo` operation retains command/reply files, daemon logs, binary SHA-256 and a report. Controls cover an empty catalog with an omitted rollout, prompt-only pending evidence, restart, removing only the owned rollout, later conversation identity, changed/malformed prompt snapshots, inaccessible versus empty sources, corrupt catalog catalog-relative paths, 64 prompt references and 301 readable rollout paths that exceed the public detail samples. Full history SQLite acquisition, catalog reconciliation, rewrite lineage, source defaults and activation remain outside this path.
