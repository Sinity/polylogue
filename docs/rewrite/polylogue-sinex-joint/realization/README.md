# Requirement coverage and first milestone tasks

This is the first translation layer for the [realization plan](../REALIZATION-PLAN.md), not a second specification or a live task ledger. The existing law tables and component catalogs own semantics and slice assignments. `tasks.json` owns six additional bootstrap obligations and five near-term task contracts per product. Beads will own execution state after the new stores are chosen and routed. Preservation gates source replacement; routing gates graph import and M1 dispatch separately. Preparing an isolated M0 candidate does not require redirecting live task stores.

## What is covered

`requirements.py` derives stable IDs (`polylogue:law:9`, `sinex:component:model.events`) and maps every indexed law/component to its owning slice epic. It keeps Polylogue's five merged laws retired, law 9's split assignment, and law 124's first-migration-release assignment. It does not infer that a prototype implements the eventual product. All active rows remain planned.

The current inventory contains 141 Polylogue laws, 51 Sinex laws, 103 components and 12 bootstrap rows. There are 21 Polylogue and 18 Sinex task nodes: preservation, task routing, executable bootstrap, first path, independent evaluation, M0/M1 outcome milestones, and deferred slice epics. Deferred epics describe intended scope; they need decomposition before dispatch. M1 acceptance is deliberately narrower than either full slice 1. Neither child counts nor a successful M1 close a slice epic.

## From requirements to the new execution corpus

Review one consumer workflow at a time across its normative owners: acquired evidence, identity/coordinates, retention, interpretation, acknowledgement, consumer answer and recovery. Map each independent obligation to an existing law/component or bootstrap ID where that ID is specific enough; add a distinct obligation only for an uncovered behavior. Resolve contradictions at the owning spec before dispatch. Record whether each reviewed obligation is assigned to a near-term task, a deferred slice, or a justified retirement. Unreviewed prose remains visible in the inventory; graph coverage of indexed rows cannot close that backlog.

Generate the future graphs from a committed spec revision after reviewing the relevant near-term acceptance. New post-rewrite tasks describe the target product route and start from its actual evidence, rather than inheriting closed status from old tasks or prototype tests. Link old IDs for intention and preservation history, and carry synthetic regression cases to their new owners. Operational work on the old deployment stays in its existing store. A delivered pre-rewrite component can inform the implementation; it does not prove the new packaged route.

Before importing, verify the new store and actor from the actual intended checkout, then reconcile every import key against existing rows. Check requirement-to-task coverage in both directions, dependency meaning, and scenario acceptance after import. A partial or ambiguous import is inspected before retry; preserved old stores and their routing are not overwritten. This procedure uses the existing requirement map and Beads graph, without a second execution ledger. Store creation/routing still needs its separately scoped operational action.

## Generate and check

From the spec root:

```sh
python3 polylogue-sinex-joint/realization/requirements.py
python3 polylogue-sinex-joint/realization/test_requirements.py
python3 polylogue-sinex-joint/realization/requirements.py --inventory
python3 polylogue-sinex-joint/realization/requirements.py --graph polylogue --revision <spec-commit>
```

The graph is native `bd create --graph` JSON, printed to stdout. Generate each project's graph into private scratch after committing the reviewed spec; pass its full SHA. An explicit revision is resolved to a commit and must match HEAD in a quiescent checkout with clean tracked/index state; graph source files must be tracked. The CLI checks those boundaries before emission and writes the resolved SHA, so an old revision label cannot describe current working-tree requirements. Unrelated untracked scratch is allowed. The default `unbound-preview` is visibly unbound and for inspection only; never import it as revision-bound work. The checker requires every non-retired indexed obligation to have at least one valid task destination; an empty assignment is not coverage. Deliberately merged/retired laws can remain unassigned. It also verifies owner files, acceptance IDs and prerequisite cycles. Existing law/outline checks still own their deeper structural checks. None establishes correct runtime behavior.

## Trial and eventual import

Use a newly initialized disposable Git repository with no `.beads` redirect. Clear ambient `BEADS_*`/`BD_*` routing overrides. Initialize embedded storage with the installed host CLI, explicit `--actor codex`, `--sandbox`, `--non-interactive`, `--skip-agents`, `--skip-hooks` and a disposable prefix. Check `bd where` before creating anything. Never initialize this spec checkout or repoint a source checkout for a trial.

Preview with `bd create --graph <file> --dry-run --json`, then import once in the disposable store. Inspect `bd show --json` for **every** mapped node: `spec_id`, status, acceptance metadata and actual blocking dependencies. Run `bd graph check` and `bd ready`; only preservation and task routing should be ready in an empty store. Inline dependency counts are not represented by the dry-run's top-level `edge_count`, so do not use that field as proof of missing or present blockers.

Before live import, choose the separate new stores/prefixes and test their actual redirects and cross-store lookup. Compare the exported graph and inventory against current store rows by `spec_id`; resolve duplicate, changed, satisfied and obsolete task contracts before writing. **Import is not idempotent:** the tested CLI permits multiple tasks with the same `spec_id`. Retain the returned symbolic-key-to-ID map privately and verify the created graph against the inventory. Do not rerun an import after an ambiguous result without inspecting the store. No automatic importer or custom scheduler is introduced here.

Reconcile each historical open task as carried behavior with new ID, satisfied with current evidence, superseded by a linked decision, deferred, or old-system operational work. Preserve old IDs and stores; do not bulk-close operational blockers because code was replaced. New acceptance metadata uses stable `{id,text}` rows. Choose actual assignees at dispatch; the role in each task description is responsibility, not an automatic claim. Dependency readiness does not authorize publication, state reset or activation.

## Verified trial and limits

The following trial predates the separation of routing from preservation; its node and edge totals describe that earlier graph. The changed graph has local checks but has not been imported into a native store. On 2026-10-13 the installed `bd` imported both graphs into one synthetic embedded store: 37 nodes, five blocking dependencies per product, matching acceptance metadata and deferred statuses. `graph check` reported no cycles; `ready` returned only preservation. A deliberate duplicate-spec-ID create succeeded, proving the reconciliation requirement. The final project-specific path descriptions were checked locally; the native import trial exercised the same fields and edges before that prose narrowing. This trial did not test live new-store routing, cross-project `ship`, leases, formulas, hosted review or service behavior.
