# Realizing Polylogue and Sinex

Status: implementation strategy, updated 2026-10-14. This plan responds to the operator’s new preference to replace **both** current source trees with spec-derived workspaces in their existing repositories. It supersedes the delivery assumption that Sinex must morph its old workspace and the assumption that Polylogue needs a long-lived `rust` branch. It does not supersede product behavior, identity, privacy, retention, or deployment decisions. Source replacement, live-state replacement, and service cutover are separate actions.

The immediate job here is to make the specification a reliable starting point for two useful products, then deliver those products in observable vertical slices. More prototype coverage is valuable when it settles a consequential uncertainty; indefinitely polishing a substitute product in this repository is not the implementation strategy.

## 1. Decisions and constraints

- **Finish and linearize existing work before M0.** Reconcile all registered worktrees, branches, recoverable edits and stashes, in-flight jobs and PRs in both repositories. Finish intended changes and land them on the actual default branch through its normal gates; identify already merged or superseded work from content and task evidence, not ancestry alone. Remove obsolete or unowned checkout leftovers only after their commits and edits have a verified disposition. Keep useful isolation checkouts with a named owner and purpose; checkout count is not a gate. Refresh preservation refs and restore-tested bundles from the resulting clean heads. M0 preparation waits for this reconciliation; source and live-state replacement remain separate. The gate covers the finite retained work: each started intention must be delivered, already satisfied with evidence, or explicitly retired by an owning decision. Preservation or deferral alone is insufficient; never-started roadmap tasks do not enlarge this gate.
- **Keep the repositories and history; replace the workspaces.** Preserve pre-rewrite refs, then ordinary replacement PRs into each repository’s actual default branch. Git continuity does not require keeping the old tree. Today both local source checkouts are clean on `master`, with `origin` configured. This is a local observation, not proof that hosted heads, other worktrees, or unpushed work match.
- **Build independent products first.** Polylogue’s standalone SQLite archive must be complete without Sinex. Sinex must capture and answer shell/browser questions without Polylogue. Their optional backend meets at the already agreed boundary, after Polylogue slices 1–4 and Sinex slices 1–2; finite shadow qualification and the rebuild proof precede native `primary` ([sequencing](topics/06-sequencing.md), [decisions](decisions.md)). A missing partner cannot stall either first product.
- **Start fresh in code, not in knowledge.** Reuse a proven primitive only after checking its interface and laws against the target design. Preserve old parser cases, failure inputs and operational discoveries. Do not import old registries, tooling, schemas, tests or compatibility paths wholesale.
- **Use a team with distinct authority.** Product owners can orchestrate their own workers; one integrator owns cross-project sequencing and releases. Runtime evidence gets a separate owner because writing code and observing its behavior are different responsibilities. This is not multiple agents voting on every patch.
- **Translate the whole intended scope into traceable work, without making prose into tickets.** Every normative requirement needs a disposition and implementation/evidence link. Narrative, examples and reasons remain documents. Beads own execution state; the specification owns semantics.

The target architectures remain authoritative: [Polylogue’s convergence loop](../polylogue-spec/spec/architecture.md), Sinex’s [identity](../sinex-spec/spec/model.md), [writer/derivation](../sinex-spec/spec/derivation.md) and [analysis workers](../sinex-spec/spec/analysis.md). NATS, archived interpretations, retained bytes and missing-value distinctions are deliberate choices.

## 2. Make the specification composable

Keep the existing layers, but give each a specific job:

| Layer | Owns | Required connection |
|---|---|---|
| Purpose, workflows, vision | The user’s question and useful observable answer | At least one consumer and example; later ambitions may remain hypotheses |
| Decisions and principles | Why a mechanism exists; settled tradeoffs | Owning behavior section and enforcement where affordable |
| Behavioral spec, catalogs and laws | Normative semantics, including failures | Stable requirement/law ID, example and implementation assignment |
| Outline and skeleton | Components, ownership, types and allowed dependencies | The real path through the interfaces, not just matching names |
| Slice plan | Delivery order and useful milestones | A complete input-to-surface demonstration and explicit non-goals |
| Evidence | Measurements, counterexamples and limitations | The claim it settles, candidate revision and reproduction |
| Beads | Ownership, dependencies, decisions pending and completion evidence | Links to the semantic owners above; no copied parallel spec |

First **check critical workflows across their contracts**. Trace these journeys through the layers: retained bytes to query; replay/archive/purge to every consumer; observations to zero/missing/Recorded cells; notes to effective values; backed publication to rebuilt standalone answers. Record disagreements at their owner and resolve connected callers/examples together.

The purge-retention disagreement is now resolved in Sinex storage/derivation: bodies and archive rows disappear, content-free delivery positions stay, and each physically removed body emits a fresh purge change even if archived earlier. The runtime probe exercises missed historical-cache invalidation and live-search removal; [its limits](../sinex-spec/evidence/reviews/purge-delivery-2026-10-13.md) keep generic purge closure and broker payload cleanup open. Implement those consequences before claiming a complete physical purge. Also distinguish newly admitted derived-parent liveness from deliberate retention of unchanged provenance after ordinary supersession; collapsing these rules would invalidate the compressed-stream design. The replay prototype now exercises writer-owned atomic cascade, but is not a generic deployed replay implementation.

Create a small requirement map, preferably extending the existing law/component/slice indexes rather than inventing a second doctrine catalog. A row has a stable ID, owning anchor, observable requirement, assigned slice/task, test/example and disposition (`planned`, `implemented`, `deferred`, or `retired` with reason). Add IDs only where existing law IDs or anchors cannot distinguish independent obligations. The map must cover non-law obligations too: cancellation, packaging, client installation, accessibility, privacy, configuration, capacity and retirement of predecessors. A checker should detect dangling links and uncovered requirements; it cannot certify that an answer is correct.

## 3. Replacement PRs: preserve first, establish a sound starting tree

### Preservation before deletion

At execution time, inspect local and hosted refs, protection rules, worktrees, dirty files, untracked artifacts and in-flight jobs in **both** projects. Record exact source SHAs and intended replacement bases. Preserve recoverable WIP and unique commits separately from the clean default HEAD. Stop or finish writers of the candidate checkout before preparing its deletion.

Create clearly named `pre-rewrite/<date>` branches at the verified default heads, and a recoverable local Git bundle containing the refs needed to restore the reviewed code history. Verify that a separate checkout can restore the expected tree. A branch is a reference, not an independent backup. Review any branch/tag for private content before publishing it; never push all refs as a shortcut. Keep private WIP, transcripts and real-data evidence in their owning private stores. No source or state is discarded merely because a preservation note exists.

Before preparing the replacement tree, close the finite retained-work gate in section 1 against the then-current default heads. Reconcile stale open-acceptance notes against the actual owning task contract and current code/run evidence: an already satisfied finite intention need not remain open because an old handoff says so. Name any genuinely unmet operational criteria separately and keep them open; neither code preservation nor completion of that finite intention proves deployment or broad operational acceptance. Keep two separate outcomes visible: recoverable checkout/ref cleanup and completed or explicitly retired feature intentions. Refresh preservation from those finished heads and verify both the restored tree and any unique WIP separately. The replacement PR is then reviewed against the bootstrap inventory; composition-skeleton compilation, graph import and component tests cannot substitute for its executable acceptance. Live package pins remain on the preserved implementation until separate cutover.

Inventory deployment/build consumers before removing their inputs: Sinnix packaging, service units, hooks, installed clients, release automation and other repository dependencies. Pin existing deployments to the preserved implementation until cutover is explicitly performed. A package upgrade must not accidentally install a workspace full of stubs.

### Three different claims

1. **Composition skeleton:** the existing std-only skeletons prove crate edges, component placement and some type ownership. They explicitly contain `todo!()` and placeholder types ([Polylogue](../polylogue-spec/skeleton/README.md), [Sinex](../sinex-spec/skeleton/README.md)). Keep them as design evidence until replaced by the real workspace; compilation alone earns no usability claim.
2. **Bootstrap workspace:** the replacement PR provides the actual toolchain/dependencies, ownership types, crate/module layout, build entrypoints, narrow xtask/AgentCTL commands, synthetic fixture support and package/service interfaces. Unsupported capabilities are explicit errors and are excluded from production registries; no reachable `todo!()` pretends to work. Build and tests run in a fresh checkout with isolated state. Pure model/identity and content-store contracts have meaningful tests, including deliberate bad inputs. Unimplemented modules may retain signatures, but cannot masquerade as supported commands or sources.
3. **First usable product:** a real daemon, writer, source and CLI/MCP path answer the first workflow and recover after interruption. This is the first user-value milestone, not the bootstrap merge.

Each replacement PR demonstrates bootstrap acceptance, explains preserved files, removes old callers/docs/tests/config together, and names lost capabilities. Keep old behavior on preservation refs, not beside the replacement. The PR may include a minimal real tracer path needed to prove executability; broader features follow.

The source repos currently have different verification rules: Polylogue uses `devtools` and protected-branch PR checks; Sinex uses xtask, database-backed local gates and hosted review. Their current `AGENTS.md` and hooks govern the replacement until the PR deliberately replaces obsolete tooling with usable successors. Do not bypass an inconvenient predecessor hook; revise the hook and its callers in the replacement itself. Recheck hosted enforcement at execution time. Publishing/merging and host activation remain outside this planning batch.

The old data policy needs its own preservation/import/cutover procedure. Polylogue’s [migration plan](../polylogue-spec/plan/migration.md) includes raw inputs no longer present at providers and purchased vectors; a code branch preserves neither. Revalidate those inventories before any state move or deletion. Sinex’s previous fresh-state decision does not authorize an unattended wipe today. Tests use new isolated state; operational resets require their own consequence-appropriate authorization and evidence.

## 4. Implementation milestones

Keep numbered product slices as semantic scope, and regroup delivery steps where fresh workspaces remove old cleanup prerequisites. Do not rename all work merely to fit this plan.

| Milestone | Polylogue | Sinex | Exit evidence |
|---|---|---|---|
| M0: executable foundation | Real model/store contracts, shared blobs, daemon/client request types and minimal build/test route | Real model/protocol/store contracts, writer/admission interfaces and isolated PostgreSQL/NATS route | Fresh checkout builds; forbidden dependency/write-access examples actually fail; no fake supported feature |
| M1: first useful path | Claude Code file → retained revision → parser → writer → search/read/export through CLI and MCP | One shell source (for example Atuin) → retained material/observation → admission → search → actual CLI; confirmed delivery and MCP remain explicit slice criteria | Independently checked fixture facts; actual clients; append, empty source, bad input and restart; operator can repeat the demo |
| M2: trustworthy daily operation | Codex/live collection, hook briefings, full query facts, web-chat imports and comparison with preserved parser outputs (slices 2–4) | Browser history, replay/derivation and shell-session path, then desktop context (slice 1 completion and slice 2) | Late/rewritten inputs, pagination/cancellation, crash recovery, truthful unknown/degraded status and measured whole-loop cost |
| M3: optional shared backend | Native adapter and identity bridge; finite fixed-basis shadow qualification; index rebuilt from Sinex; `primary` only after the decisive proof | External ingress and replicated frontier; retained content and projection rebuild contract (slice 6) | Same archive/query answers across modes, partial send/retry/outage, excision propagation, two archives and real-corpus rebuild |
| M4: breadth with consumers | Remaining providers, lineage, notes, semantic search, reader and analytics | Lake imports, bulk throughput, native capture, Lynchpin products and reading/briefing surfaces | Each source/product meets a named user workflow; provenance, opportunity and invalidation survive its actual path |
| M5: workbench and richer reasoning | Later pages/investigations/agent collaboration | Richer analyses and higher-order products | Repeated use validates the consumer; no layer built only because its types were easy to generate |

Deliver M1 promptly. Polylogue slice 1 is broad: distinguish its first runnable path from full slice completion. Sinex’s first shell search likewise leaves replay/automata obligations open. Measure bottlenecks instead of treating day estimates as acceptance.

For each step: settle types/examples, assign ownership, implement the path, run focused checks, integrate, run affected broader checks and inspect output, then commit/PR with residuals. Parallelize providers/pure modules after interfaces are real; one owner holds storage/schema and shared registries.

Promote prototype implementations selectively into production modules and rerun the same cases through the production route. Once the real route covers a prototype’s purpose, retire its duplicate implementation or keep only an independent reference evaluator. The product must not depend on Python prototypes as runtime authorities.

## 5. A small team, without duplicated command

| Owner | Authority and output | Boundary |
|---|---|---|
| Polylogue product lead | Standalone workflows, slice designs and worker allocation | Cannot redefine Sinex admission/storage semantics |
| Sinex product lead | Capture, replay, derivation and analysis workflows; workers | Cannot weaken standalone Polylogue or choose backed mode for it |
| Joint integrator | Shared interfaces, integration candidate, dependency order and release decision | Resolves interface conflicts from owning decisions/evidence; does not rewrite both leads’ contracts silently |
| Runtime evaluator | Owns a named client/integration scenario at milestones; runs the fixed candidate and reports discrepancies | Adds runtime evidence, not another per-patch reviewer or approval gate; expectations are independent of implementation output |

The evaluator derives expected behavior and the tested input domain from the owning current contract at the recorded revision. Oracle independence means computing expectations without calling the implementation; it does not authorize stronger requirements. For example, repeatability for one fixed input does not by itself require an invariant across arbitrary interleaved histories. Report a stronger exploratory property as a proposed semantic change, and settle it at the owning spec before making it acceptance. If evidence shows an oracle encoded the wrong requirement, correct that oracle and its explanation rather than adding production state to satisfy it; preserve every criterion the actual contract requires. This uses ordinary author review, not another approval tier.

For a joint delivery, the integrator freezes the exact producer and consumer revisions, protocol/configuration and test state before the runtime evaluator runs the joined route. Each lead supplies the owned entrypoint and residuals; a fix on either side invalidates only the affected joined evidence and gets a new candidate pair. Component proofs remain reusable within their recorded scope. A merged producer or consumer alone does not close the joint outcome.

For source-conservation scenarios, the product lead owns the acquired format and reconstruction dependencies; the runtime evaluator checks the packaged consumer against independently retained fixture facts after the original provider path is changed or removed. The joint integrator owns the cross-product case when optional transport is involved. Their result distinguishes acquired bytes, reconstructed input and normalized answer, and names any untested boundary.

Product authors retain ordinary correctness review and scoped verification. Roles are responsibilities, not four permanently running agents. One agent can hold several roles during a small step; consequential E2E evaluation should use fresh context and the declared examples. Add a dedicated architect only for a named unresolved design question, not as another continuous approval tier. Hosted review remains the independent code review where available.

Every task has one owner, write scope and integration destination. Give workers relevant spec/rule anchors, existing interfaces and acceptance cases, not the entire archive or authority to improve adjacent architecture. Use isolated worktrees for independent leads and AgentCTL workers. A tightly coordinated shared checkout may be used only with disjoint ownership and enforced prohibition of worker Git/index mutations, as the current method requires. One integrator changes shared manifests and lands changes after workers finish. AgentCTL owns jobs, Git owns candidate revisions, Beads owns tasks; a separate team ledger would duplicate authority.

## 6. Inspectable end-to-end testing

For each milestone, provide one reproducible demonstration directory/script with synthetic input, independently stated expected facts, commands and a short readable result. Run the packaged binaries and actual CLI/MCP/socket/HTTP routes, not just their handler functions. Use real SQLite or PostgreSQL/NATS where their guarantees matter. A run records candidate SHA, executable revision, environment/schema identity, exact commands, exit statuses, assertions, timing/resource measurements where relevant, and links to raw logs in the owning run store. Existing AgentCTL and xtask history provide execution identity; do not invent another receipt system.

The operator should be able to open one local HTML page or Markdown result and see: the question asked, the exact returned answer, why it is correct, the failure/recovery sequence, and the command to repeat it. Screenshots are appropriate for a browser/rendering claim; machine-readable output and retained source coordinates settle data claims. Show expected versus actual output and untested scope. Generate summaries from recorded outputs; never turn a status boolean into a proof.

A result names the boundaries it actually exercised. Separate codec/handler checks, real storage/bus component tests and the packaged authenticated client-to-client route. For an optional-backend milestone, the joined run starts with the actual source acquisition/outbox and crosses the real API, immutable content store, ingress bus, sole admission path and query/confirmed consumer. Exercise a lost final reply and restart/retry of the same intent: inspect accepted immutable content, actual terminal acknowledgement and consumer progress independently. A synthetic HTTP server, direct stream publication or manually assembled request may qualify its component; it leaves the omitted boundaries open.

The milestone's existing readable result lists each required scenario as exercised with its exact expected/actual output, failed, or unrun, with the candidate pair and run links. Source conservation includes all contributing originals and attachments; byte windows and logical exports keep their declared scope. Summaries count only what was observed. The repeat command reaches the same isolated endpoints, and an operator can inspect the failure/recovery sequence without reading every agent transcript. This is a view over the run evidence, not another status authority.

The result must also be emitted when daemon launch, client execution, comparison or a timeout fails. Capture raw stdout/stderr and exit status before comparing; preserve them through owned-service cleanup. An absent answer is shown as absent with the launch/client failure, never an invented empty result. Mark dependent scenarios unrun with the blocking reason. Successful rendering does not change a failed run's nonzero exit status. Acceptance deliberately supplies a wrong answer and a failed launch: both runs fail, yet the same readable result exposes the expected value, actual value or its absence, cause, raw-run links and repeat command. This is a requirement for the milestone runner, not a new reporting service or evidence of its implementation.

Minimum destructive/failure scenarios follow the affected path: process kill between durability boundaries; restart and retry; delayed/duplicate inputs; malformed input among valid rows; parser/recipe change; late records and empty polls; archive/cascade/purge through search, analysis and downstream publication; consumer outage and resume. Test paging, cancellation and bounded-memory work on generated large inputs before private-corpus runs. Target the specific invariant a test can falsify; one known-bad input/mutation per law checks the oracle without hand-written boilerplate in every test.

Source-conservation demonstrations include a full capture followed by an append window, reconstruction requiring earlier retained parts, and a SQLite snapshot/row-export distinction. Change or remove the original path after durable retention and before the actual ingress/parser route runs; restart and retry of that registered acquisition must return the same retained evidence and answer. Include one missing predecessor or attachment and one explicit unknown capture interval: expect the declared unavailable/partial outcome, never current-path substitution or fabricated completeness. Capture the contributing immutable identities and coordinate basis so the operator can inspect which original bytes support the normalized result. These are required scenarios for the source paths that support them, not a claim that a prepared fixture or plan has exercised them.

Use the reference evaluators to calculate expected answers independently, then compare incremental production results with fresh reconstruction from retained source evidence. The fixture builder must not generate expectations by calling the implementation under test. Comparison with old parsers is a discrepancy detector, not a rule that old bugs must be preserved.

Public evidence stays synthetic. Private inputs, captures and outputs remain in their owning stores; public PRs report safe aggregates and limits. Masking does not authorize publication. Personal-corpus and installation runs require scoped authority. Isolated tests do not prove the deployed service or operator’s actual client; verify those at cutover.

Do not make operator availability a blocker for every code task. Offer milestone demonstrations for inspection; claim agent verification separately from operator usefulness. The daily-use/cutover milestone requires the operator’s experience or the real client workflow it names, and stays open without that evidence.

## 7. Beads: complete scope, small executable work

Use separate post-rewrite stores for Polylogue and Sinex with unambiguous new prefixes and explicit routing. Preserve the existing databases as historical records; changing a checkout’s `.beads` redirect affects the whole project, not just its branch. Plan store creation/routing as an operational change, test it first in a disposable context, and choose names before importing. Do not reset, bulk-close, or overwrite old stores. Keep old IDs resolvable or link to their archived exports from the new store.

The installed host `bd` is 1.2.2 (dev), inspected on 2026-10-13. Its CLI exposes `create --graph`, `--dry-run`, `--spec-id`, structured metadata, `decision`/`spike`/`milestone` types, typed dependencies, claims/leases, graph checks/HTML, formulas/molecules, async gates and cross-project capabilities. Help establishes availability, not that cross-store routing or a workflow watcher is configured. Verify those in a disposable store before relying on them.

### Translation and import

1. Inventory normative requirements from specs, catalogs, laws, workflow acceptance, decisions and set-aside lists. Preserve references to the spec revision. Review for omissions and conflicting requirements before scheduling.
2. Assign each requirement to a useful slice epic. One implementation task covers a complete narrow behavior through schema, logic, surface and tests; many laws may belong to it. Decision tasks answer one sharp unresolved question. Large later scope remains deferred/planned, with requirements mapped, rather than thousands of speculative function-body tickets.
3. Prepare a graph import with titles, owning anchors, write scope, observable acceptance, verification commands and real prerequisite edges. Trial the importer and schema in a disposable store; preview/deduplicate against `spec-id` or a stable import key, then import into the new stores. Import is not evidence of completeness: compare the resulting graph back to the requirement inventory.
4. Use `blocks` only for genuine prerequisites. Use origin/related/supersession links for discoveries and old work; they do not automatically block execution. Group tasks sharing files or one verification boundary under one owner. An epic closes against its required dependency edges and outcomes, not child counts.
5. Create a reconciliation table for old open tasks: carried behavior with new ID, already satisfied with code evidence, rejected by a newer decision, deferred, or operational work still belonging to the old system. Reuse the existing [Polylogue switchover work](../polylogue-spec/evidence/beads/beads-switchover.md) and Sinex audit/area assessment as inputs. Do not close historical operational blockers because code was replaced.

Task bodies link to the spec rather than copying it. Store stable acceptance IDs once, with observable text; consume only metadata that dispatch or coverage actually reads. A close note names the delivered commit/PR, result and residuals. Operational criteria remain open until run evidence exists. No closure manifest engine or product-side proof machinery is added to compensate for false closures.

Use `bd ready`, claim/lease/reclaim, `graph check` and `graph --html` for execution and operator inspection. Cross-project `ship` capabilities can represent genuine versioned prerequisites such as tested admission protocol support; use them only after routing and closed-provider resolution are exercised. They cannot prove runtime compatibility by themselves. Try one formula/molecule only after two slices reveal a repeatable useful workflow; gates are useful for real external waits such as PR completion, not obligatory ritual between every edit. No custom scheduler beside AgentCTL.

Requirement changes update semantic owners and affected task contracts/edges; reopen invalidated acceptance and record supersession. Replan at milestones or when the critical path fails, rather than regenerating every ticket.

## 8. Prevent the previous failure modes

The causes are already documented in [Polylogue lessons](../polylogue-spec/plan/lessons.md), [rewrite rules](../polylogue-spec/plan/rewrite-rules.md) and [Sinex’s growth history](../sinex-spec/evidence/history/ai-history.md). Use their existing enforcement owners.

| Observed cause | Prevention with a concrete result |
|---|---|
| Codebase development without useful software | First runnable workflow before broad infrastructure; each later component names the consumer using it |
| Parallel read/write/ingest routes diverge | One typed owner and production path; CLI/MCP/export parity on the same input; forbidden-edge check demonstrated failing |
| Unknown or failed work displayed as zero/healthy | Value/outcome types carried to real client output; missing/partial/Recorded and degraded cases independently checked |
| Mechanisms lose their reasons | Decision links beside consequential boundaries; inspect the current ruling before removing NATS, provenance or retention |
| Topology changes leave old machinery | In the same change enumerate and retire old roles, callers, config, commands and tests |
| Audit findings accumulate machinery | Reproduce the actual defect; compare the smallest semantic fix; reject irrelevant threats and vocabulary |
| False closure grows closure bureaucracy | Reopen the task and fix the observable behavior; do not add permanent certification code |
| Huge self-confirming tests | Shared small examples, independent expectations and deliberate failing cases; broad runs at coherent milestones |
| Arbitrary caps hide throughput/memory problems | Streaming/paging and whole-loop measurements including writer/derivation, not parser speed alone |
| Developer tooling becomes a second product | Extend a tool only for a concrete blocked slice or measured repeated cost; retain no unused command merely for completeness |

Review each coherent change once for wrong observable output, contradicted decisions, and avoidable concepts. Surface diffs make new commands/tables/states visible; they are information, not a score or arbitrary growth ceiling. Cheap nearby corrections belong with the change; substantial independent findings become linked work. This keeps rigor directed at software rather than at paperwork.
