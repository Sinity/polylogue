# Joint glossary

Words whose meaning both projects share, or deliberately do not. Each project's own glossary owns its own words (`sinex-spec/spec/glossary.md`, `polylogue-spec/spec/glossary.md`); this file holds only the pairs and the shared distinctions.

| Term | Meaning |
|---|---|
| **state as of T** (Sinex, `as of T`) | what the system believed at T: the interpretations live then, under the rules and parsers of then. Answers "what did Sinex say last Tuesday?" |
| **evidence cutoff** (Polylogue, `evidence_until:`) | the evidence available up to T, read with today's parsers, prices and excisions. Answers "what does today's reading make of what existed then?" |
| **the same** | never unqualified. Seven questions with different evidence: same bytes (digest), same record location (material and record address), same source record (the source's key), a newer version of it (the source's revision order within its namespace), same interpretation (event ID), same occurrence across sources (a shared identifier, an operator assertion or a rule's inference, recorded as the association's basis), counted once (a metric's unit and policy). `sinex-spec/spec/model.md` §6 and Polylogue's `model.md` hold each project's version; `sinex-spec/evidence/reviews/identity-review-2026-10.md` §1 is the source |
| **one store** (joint decision 27) | in Polylogue's `primary` mode, Sinex's content store is the only physical store of source material; in `off` the two projects keep separate stores of one format; finite shadow qualification does not change standalone authority. "Shared" always says whether a format, an implementation or a physical instance is shared |
| **resolved object** (joint decision 28) | what Polylogue publishes: a session or message already merged from its routes, carrying references to every contributing input revision. Sinex stores and projects it and never re-derives conversation meaning |
| **removed at source** | the source no longer exposes a record; inferred from a later snapshot only inside that snapshot's coverage (an account export, a rolling window), never from a missing part. Both projects keep the evidence. They differ deliberately in views: Sinex leaves such records out of ordinary views and counts by default (`sinex-spec/spec/storage.md` §7); Polylogue keeps a gone session in ordinary views (`source: gone`, `gone_at`), because keeping what providers delete is its archive's purpose |
| **`pl.` / `sx.`** (joint decision 29) | the project prefixes of a cross-system query's collections; mandatory where a word means different things in the two projects: `session` (a conversation, an activity session), `event` (a harness event, a Sinex event), `near` (semantic ranking, a temporal window) |
| **replicated frontier** (joint decision 29) | the largest Polylogue write counter W whose revisions are all complete in Sinex; a cross-system result is compatible when W reaches the Polylogue state it reads, and otherwise waits or reports the lag |
| **time quality and precision** (one vocabulary, no translation) | every time in both projects says where it came from (`time_quality`: `captured`, `intrinsic`, `file_mtime`, `file_ctime`, `operator`, `staged`, `unknown`) and how exact it is (`precision`: `instant`, `second`, `minute`, `day`, `month`, `year`, or `bounded` with `until`). A coarse or bounded time stands for its whole period in temporal joins (joint query law "Coarse times"); a day is the calendar date in the source's zone, never moved to a logical day. Polylogue's own bases map onto it: provider and commit times are `intrinsic`, Drive and ZIP entry times are `file_mtime` (Drive bounded, ZIP to the second), and an offsetless local time is `intrinsic` with its assumed zone recorded. `sinex-spec/spec/model.md` §5 |
| **candidate** (two meanings; qualify in cross-system text) | Sinex: an output of `recompute` under another producer version, kept apart until compared and switched or dropped; also a candidate claim, an interpretation awaiting judgment (`sinex-spec/spec/glossary.md`). Polylogue: the candidate set a query stage produces before ranking. Write "recompute candidate" or "query candidates" where both projects are in view |
| **archive** (two meanings; qualify in cross-system text) | Sinex: where past interpretations are kept (archived events, the `archive` unit); an "export archive" is a provider's ZIP. Polylogue: `archive.db` and the archive as a whole, the store of conversations. Write "Sinex's archived interpretations" or "Polylogue's archive" across the boundary |
| **generation** (two meanings; qualify in cross-system text) | Sinex: a database generation, the counter in a row-ID key that a poller raises when a database is recreated. Polylogue: an index generation (GEN in change cursors). Always written with its noun ("database generation", "index generation") |
| **witness** / **match** (one meaning each, agreed 2026-10-12) | a **witness** is one source's observation of an occurrence, the operator's word in both projects (Sinex fuses witnesses; Polylogue keeps routes as separate witnesses). A **match** is the row a query's join, `exists` or `seq` selects to justify a result row; the joint query law "Match order" says enumeration order never changes it. The query sense was called "witness" until 2026-10-12 |

| **unparseable time** (the rules differ, deliberately) | a time present in a record but in a format the parser cannot read. Sinex makes the record a record error, because many Sinex keys include a time and a time-less record would merge with every record sharing the rest of its key (`sinex-spec/spec/sources.md` §1.3, law L49). Polylogue keeps the record with its time unknown and counts it as `time_unparsed`, because no Polylogue key uses a parsed time: provider IDs carry none, and fallback IDs hash the record's raw text and an occurrence number (Polylogue law 136). A missing time is unknown in both projects |
| **parser upgrade** (the projects differ, deliberately) | Polylogue converges: after a parser version change, every revision chain of that format is re-parsed, and affected results read `up_to_date: false` until it finishes. Sinex replays explicitly, because replay is the operator's primitive: a parser fix reaches only the materials a replay names, and materials and sources carry `behind` (some live events read by an older parser than the one running) so a skipped material is shown, not silent (`sinex-spec/spec/query.md` §3.2, §3.5). Either way an old reading never passes as current |
