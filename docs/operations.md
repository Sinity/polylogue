# Operations

Running Polylogue: the daemon's lifetime, its idle and steady-state work, the halt state, `status` and its check of every stored byte, notices, and the change feed. Setting up and keeping an archive (installing, configuration and `set`, `embed`, `demo`, deployment, upgrades, backup and restore) is [installing.md](installing.md).

Neighbouring facts live elsewhere: the durability order and pipeline are [architecture.md#durability](architecture.md#durability) and [architecture.md#pipeline](architecture.md#pipeline); the command forms and exit codes are [interfaces.md](interfaces.md#commands) and the latency classes are [latency.md](latency.md#latency-classes); the orientation screen is [terminal.md](terminal.md#the-orientation-screen); the schema tools are [archive.md#schema-tools](archive.md#schema-tools); Polylogue on Sinex and its [rebuild](primary-mode.md#rebuild-and-parser-upgrades) are in [primary mode](primary-mode.md); the signal rule schema and its evaluator are common's [signals](https://github.com/Sinity/polylogue-sinex-common/blob/master/crates/signals/README.md); the web views of status, notices and settings are [web.md](web.md).

No command checks for a terminal or harness variables to decide whether it may run; every write records its computed author ([authorship.md](authorship.md)); every command shows stored text as it is, censoring nothing. There is no repair, reconcile, reindex or reset command and no scheduled check ([architecture.md#principles](architecture.md#principles)).

## The daemon

Polylogue runs as one resident daemon per archive, `polylogue daemon [--until-idle] [--no-sources]`. The daemon is the only process that opens the archive; every client (CLI, MCP, hooks, the web UI, the browser host) is a thin client of its socket, for reads as well as writes. It exists so that Polylogue replies at interactive speed and so that what should be happening can be seen happening.

**Start.** `polylogue daemon` runs in the foreground under a service manager (a systemd user unit on Linux). In order, it:
1. raises the open-file limit;
2. takes the archive lock, an exclusive `flock` on `<archive>/lock` opened through the resolved directory path, and writes its pid into it; a second daemon on the same archive, by any path, exits 1 naming the pid of the daemon that has the lock;
3. opens `archive.db` and `embeddings.db` at the current format, adding to an `embeddings.db` from an earlier build the tables added since, or refuses with exit 78 when either is in another format, naming the version it found for `archive.db` and what differs from the nearest schema for `embeddings.db`; the refused file is left exactly as it was ([archive.md#evolution](archive.md#evolution));
4. opens `index.db` at its saved positions; with no index, or one written for another schema, it builds a new one in a private file and installs it when the build ends ([installing.md#replacing-an-index-from-another-schema](installing.md#replacing-an-index-from-another-schema));
5. opens the segment log at its last recorded blob, or stops when the segment holds more than an unfinished put past it ([restoring `archive.db` alone](#restoring-archivedb-alone));
6. binds the socket, serves requests, then starts its work.

No step rewrites `archive.db`, the segment log or the embeddings store to get past a format difference; the only change at open is adding new tables to the embeddings store.

**Readiness.** With `Type=notify` the daemon signals readiness once the socket responds to a liveness request, before catching up. The connection's thread responds without a reader or any cache, so a vector load or a full reader pool never delays readiness or the watchdog. Catching up is shown as work in `status`, never as unavailability.

**Steps.** Opening and stopping each run as named steps. Each step's end is logged with its duration (`opening: starting the writer took 0.412 s`), and the service manager's status line names the step in progress (`Opening: starting the writer`, `Stopping: engine drain`); while serving it reads `Serving`, followed by the index build's progress while one runs. A step still running after 10 s is logged every 10 s with what each busy thread is doing and the statements it has run for more than a second, which names what the step waits on. While opening, the daemon extends the service manager's start timeout by 60 s every 10 s, so a long open never times out while the process reports, and one that stops reporting does. Every logged duration is in seconds with three decimals.

The daemon and hosted-session sockets appear at their public paths only after they listen. Clients waiting for archive opening observe socket publication and closure of the archive's writer lock, bounded by the caller's deadline. A failed open releases that wait even without a deadline. Hosted-session startup observes socket publication or child exit; its deadline stops the pending host's process group, and the same reaper owns the child through startup and the running session. These waits use filesystem and process notifications rather than timed connection retries.

**Stop.** On `SIGTERM` or `SIGINT` the daemon stops accepting connections, refuses new requests with `shutting_down` (a stream the stop cuts ends with that as its final answer), and makes its one stop request, which the archive it opened carries. Everything that reads or waits observes that request by how it is made, not by a check at each site:

- Every reader the store hands out checks it in its SQLite progress handler, so a read in progress (a client's, the loop's planning) ends within a thousand SQLite steps, and a wait for a reader slot or for the write lock wakes. A request's own cancellation (its client hanging up, its stream dropped) is a child of the stop request, so the stop also wakes the request's other waits: for room in the writer's queue, for the next commit, for a warm cache. A read the stop ended replies `shutting_down`.
- The loop and its shared parse pool workers run under the stop request, so the connections the store opens there observe it too, source files and stored bytes are read in 64 KiB parts with a check before each, and parsing stops between steps. A stopped parse makes no private reading visible, advances no checkpoint and records no failure; the source bytes it already prepared go through the writer and commit as usual. Queued jobs do not start, and a submitter waiting for room in the parse pool returns. The request wakes a loop waiting between passes.
- The writer's reconstructible work observes it: a derive pass ends after its transaction in progress, a build's deferred indexes end at the statement in progress and its private file is synced so the next start resumes the build, and replay of stored bytes or a copy of an identical chain's reading rolls back its unfinished index transaction, keeping earlier completed copies and the previous cursor. A recorded parse refusal or failure still commits its diagnosis, and inline assets or a refusal in another input do not keep replay running. Captures of new bytes and writes already handed to the writer finish and reply: the stop never withdraws a write its producer handed over.
- The signal worker ends, persisting the delivery records it already holds.

Running requests then get 5 s to end after the transports stop; the daemon stops without any that ignore their cancellation and logs how many it left. It leaves committed SQLite write-ahead logs for the next open, records how the run ended and releases the lock. A second signal ends the process at once, which is safe because the next open resumes every state a crash can leave; it is logged with the step it cut short. Committed progress stays; the next start completes any unfinished indexing, derivation or replay from its committed positions. Target: a stop within 5 s. The stop's steps (see Steps above) are request intake, the socket, HTTP, running requests, each application worker, the engine and the writer.

**How each run ended:** `clean` (with the signal), `refused` (exit 78, with the reason), `failed` (with the error kind), or `unknown` (no record: killed or crashed). `status` shows it. An `unknown` end is never given a cause by closeness in time to another event.

A continuous application worker that ends unexpectedly fails the run after cleanup. The signals worker keeps its original failure through its join, including a delivery worker's error, rather than replacing it with a channel-closed message. Checkpoint or delivery-record failures do not discard the existing state or bypass writer and archive-lock teardown.

Daemon and hosted-session messages carry service-journal priorities: errors for lost work or a stopped worker, warnings for work kept for retry or degraded operation, and information for lifecycle events and recovery. CLI and hook diagnostics remain plain text. A failed spool write logs once when it fails and once when it recovers. So does every failure a pass of the loop ends with: a file, location or step that failed is a warning naming it, with what ends the failure (`transient`, `content`, `request`, `environment`, `stored_data`, `bug`, `stopping`) and its code; a whole pass that failed is an error. The same subject failing again for the same cause and code is not logged again, whatever its message says, until a pass reads that file (or walks every source, or for a failed pass, completes) without meeting it; that clearing is logged once. A panic no request or parser catches is one error record naming its thread, with its location, and its backtrace on the journal lines after it.

**Liveness.** With `WatchdogSec`, the daemon sends a liveness request to its own socket on a timer, at half the watchdog period, and feeds the watchdog when the socket answers, so a process that no longer serves its own socket is restarted by the service manager. Slow or stuck work is not a liveness failure: it is reported as stalled, never restarted away, because a restart would hide the defect that caused it.

**Restart** resumes from committed positions; it does not rescan the archive, replay tool-database captures or re-read history. Target: socket ready within 2 s of start.

**Requests during stored parsing.** A queued import returns chunks that no worker has started to regular planning. Chunks already in hand commit and their parser readers drain before the loop replies through the normal import path, then reloads committed source and parser positions before continuing. Work not committed is selected again from those positions; planning for a selected import reads only those inputs' revision and observation history. No input is truncated or marked complete by the yield. An unfinished private replacement reading is dropped without changing its previous committed reading. These are request-driven boundaries, not limits on file size or the amount an archive may contain.

**Batch mode.** `polylogue daemon --until-idle` runs the same pipeline and exits when no unit has work, printing a summary (as JSON with `--json`) and exiting 0, or 1 when a pass or import met an error: the passes and imports it ran and their work added together (inputs seen and changed, bytes read and stored, messages written, sessions derived, unreadable roots and errors). "No work" means a pass ended with no capture continuing, no request queued and no change waiting from the watcher. Tests, benchmarks and the restore drill use it; it is not a second engine.

**Without sources.** `polylogue daemon --no-sources` reads none of its sources: no root is scanned or watched, no spool or tool database is read, no collector runs and no repository lookup is written, so no input, observation or coverage is recorded from the machine. It plans from stored source identities, recorded parser paths and chain progress, without reconstructing watched machine locations. It parses and derives what the archive already stores (an index behind its archive catches up, a reading-version change re-parses) and serves every request, `import` included. A file that has gone from its location is not observed as gone, because nothing looked. With `--until-idle` it processes what is stored and exits. An archive that receives another archive's contents (`import`) is started this way, so that none of its locations is watched before the import, and the restore drill uses it to check a restored copy without touching the machine's live files.

**Exits:** 0 clean stop; 1 a run that failed, or the lock held; any other failure to start serving by its failure kind ([interfaces.md](interfaces.md#exit-codes)), 4 for an archive directory it cannot create or open; 74 storage failure (the disk failed a sync of `archive.db`; [operations.md#storage-failure](#storage-failure)); 78 refused archive (`archive.db` or `embeddings.db` in another format; an index never causes it). The service sets `RestartPreventExitStatus=74 78` and restarts after any other end with a growing delay (5 s, up to 5 min). A notification is sent after every end the service manager did not ask for, restarted or not, since no daemon is running to send a notice.

### Storage failure

Each writer of `archive.db` syncs its log after each commit ([architecture.md#durability](architecture.md#durability)). When that sync, or the sync a writer makes when it starts, fails, the daemon stops writing for the rest of the boot:

- **It stops.** The writer stops at once, so no request gets a reply after the failure, not even a retry that would find its rows already stored. The journal names the file and the operating system's error number (`storage I/O error syncing …/archive.db-wal: … (errno 5); writing stopped for this boot`), and the daemon exits 74 however the run ends: a stop signal or an idle end that arrives with the failure still exits 74 and keeps the failure. The service does not restart it.
- **It stays stopped until the machine reboots.** The failure is kept in the archive's runtime directory with the boot's identifier, and a daemon started again in the same boot refuses with the same message and exit 74 (a machine without a boot identifier keeps nothing, and only the stopped process refuses). After a failed sync the kernel may have marked the unwritten pages clean, and they stay in the page cache across a process restart, so no later sync in that boot can show that they reached the disk. A reboot drops the page cache.

Recovery:

1. Check the device and the filesystem: `dmesg` for I/O errors; on btrfs, `btrfs device stats` and `btrfs scrub`. Replace or repair the device before writing to it again.
2. Reboot.
3. Start the daemon. Opening the archive recovers it as after a crash: SQLite's log recovery keeps only the frames whose checksums hold, ending at the last complete commit, and a segment tail past its last recorded blob is cut.
4. Run `polylogue status --verify` ([operations.md#checking-every-stored-byte](operations.md#checking-every-stored-byte)) and restore from backup if it names a problem.
5. What the lost commits held is read again where its source still has it. Files that tools keep where they wrote them (session logs, the hook spools, which are never deleted, and the browser host's capture logs) are re-read from their source positions, which are saved only for committed rows. Not re-readable from the machine: a tool database row the tool has since deleted; a file a tool has since pruned or rewritten; an AI Studio prompt revision whose spooled body the Drive collector removed after delivery (only Drive itself or a Takeout has it); an export, which is stored again only by importing it again. Records written through Polylogue itself (notes, tags, judgments, settings and other annotations, and query runs) have no other source; one whose commit was lost is gone, and the client that wrote it was not told it was stored, because the writer stopped before replying.

### Restoring `archive.db` alone

Putting back an older copy of `archive.db` beside the segment log and index of a later run leaves a segment holding blobs the older record does not name. The daemon's start does not cut them off: the segment's open compares the end the record names with the largest end any commit recorded (kept beside the segment), and stops, naming both lengths, when the segment holds bytes a newer record committed. Nothing is changed. To go on from the older record, put back the segment directory from the same copy, or the newer `archive.db`; to keep the newer bytes the older record lacks, import them again where their sources still hold them.

## Idle and steady-state work

Workers following commits log a failure once at error priority, a changed error once more, and the return to successful work once at information priority. A transient failure waits for the next commit before another attempt. Other causes halt the work until restart. Waiting for an index rebuild is normal work and waits for the install commit. A failing or halted worker stays in the thread activity and appears under status problems with its name and error.

An idle daemon reads and writes about as much as changes:
- With stored readings current, a pass with no changed inputs reads no stored input bytes and runs no archive-wide chain planning. Startup and parser upgrades resume from committed reading progress; completed chains stay finished across passes and restarts. With sources off and stored work finished, the loop blocks for a request or stop.
- Discovery is event-scoped. A full scan of the declared locations runs only at start and after a watcher error or overflow, never on a schedule.
- Busy tool databases are captured on the tool's own change signal (its write-ahead log, its modification time) or a minimum interval, never in a zero-delay loop.
- Idle, the daemon truncates its SQLite write-ahead logs; `journal_size_limit` is set.
- The accept loop blocks; nothing polls.

**Targets:** with nothing changing, under 1 MB/h read, no writes and under one wakeup per second; with live agents writing, read bytes at most about twice the bytes appended to watched files; memory idle and caught up under 1 GB excluding vectors (a target, not a cap). `status` shows the daemon's own I/O over the last minute and hour and the time and reason of the last full scan.

**Interactive work never waits behind bulk work.** Requests that need the whole archive (schema inference, the storage check, imports) run at idle priority. Each request runs on the thread of the transport that accepted it, and what bounds running work is the store's: the read pool for reads and the writer's queue for writes. The read pool has one connection per configured worker and one for idle-priority work, and one more that only interactive replies (status, completion and `brief`) may take; idle-priority work (schema inference, the storage check, imports, vector counts) holds readers from one request at a time. `status` without `--vectors` or `--verify` takes no reader: it reads only the daemon's snapshot and its own state. A request that waits for something other than its own computation (the next commit, for `read --follow`; a provider's query vector) holds no reader while it waits. An authored write waits at most one writer group. A read whose client has gone stops at its next step: one watcher thread notices every client's hang-up and cancels that client's reads, without cancelling work another reader needs.

**Sending never holds a reader.** A finite reply is computed, released from its reader and then sent. A stream's producer writes into a buffer that keeps up to 1 MiB in memory and the rest in a temporary file in the staging directory, so its read transaction lasts as long as producing takes, never as long as a slow client takes to read; a client that stops reading holds only its connection and the buffered bytes, and the write-ahead logs still checkpoint. Every send follows one rule: it waits for the client until the request's deadline (a send past it takes only what the socket accepts at once) or until the client hangs up or the daemon stops, and the access scope is checked before each piece sent. Each connection has one thread, which reads its requests and sends their replies.

**The halt state.** Every declared unit of work (a source location, a parser module, a derivation, the embedder, the sampler, the signal evaluator, the primary-mode sender) has exactly one halt state, read from one place:
- **unschedulable:** a halted unit is left out when work is selected, so nothing downstream of it takes the writer, forms a group or spends a budget;
- **reported:** the halt is saved, with its typed reason and the input or step that produced it; `status` names every halted unit, and a daemon with one is `degraded`.

A halt survives a restart and clears only when what it depends on changes: a new revision of the input, a new parse version of the parser, a configuration change, or a new binary. No command clears a halt.

**Stalled** is distinct from halted and from busy: work pending and no committed step for 10 minutes. `status` keeps idle, busy, stalled and halted apart.

## Status

`polylogue status [--line] [--vectors] [--verify [--manifest FILE]] [--log] [--watch] [--wait D [--after N]]` is the health of the daemon and the archive. Without `--verify` or `--vectors` it replies in the status latency class from the daemon's status snapshot and its own state, and reads nothing from the archive while answering: the worker that brings the scope index forward reads the snapshot after each commit (each batch and each hook event, [latency.md#warm-state](latency.md#warm-state)), so a reply never waits for a read connection, the writer or a query whose cost grows with the archive, whatever a pass is ingesting. A reply right after a commit can carry the figures from before it until the snapshot is read again; running sessions' states are computed at the time of the reply from the live facts the snapshot read. The daemon reads the first snapshot before it serves requests. `answers_from` says what the reply's archive figures come from: `snapshot` with its `read_at`; `build` while an index is built and none can be read, when the build's progress (`index_build` and `build_progress`, read together) is the content; or `not_read_yet` with `since` `start` (no snapshot read since the daemon started, as when the index could not be opened) or `install` (none read since a built index was installed). A reply without a snapshot has no `store`, `notices`, `running` or `quota`, is degraded, and its note, the view's headline and `--line` say the same words: "figures not read yet since the daemon started" or "figures not read yet since the new index was installed". An index rebuilt beside a readable one leaves the reply answering from the snapshot, with the build beside it and the figures the installed index's. `totals_error`, `quota_error`, `notices.error` and `running.error` carry only errors of a read the snapshot made. Every reply says whether the daemon has `caught_up`: no index is being built, no pass is running or due, derived figures and search text are current, and the snapshot was read after the latest commit. Parse states the daemon cannot finish by itself (an input with no parser, missing earlier bytes, a record still being written) do not hold it back. `changes` counts the changes to what status reports since the daemon started (the loop starting or ending work, a snapshot read after a commit). `status --wait D` replies once the daemon has caught up, or when D passes, with the status as it then is; `--after N` waits for a reply that caught up after the count passed N, the `changes` of an earlier reply, so a client waiting for a change the daemon has not seen yet (a file it just wrote) waits for the next caught-up status after it. The wait follows the daemon's own changes and polls nothing; it gives up its executor place while it waits. Bare `polylogue` off a terminal prints the same block; on a terminal it prints the orientation screen, which is built from the same snapshot ([terminal.md](terminal.md#the-orientation-screen)).

`status` shows, in order:
1. **Daemon:** pid, uptime, binary version (crate version and commit), parse versions in force, the previous run's end, whether the scope index briefs answer from is loaded (`warm.scope_index_loaded`), I/O rates, and pacing under I/O pressure with the pressure measured.
2. **Up to date:** `up to date`, or what is behind: an index being built (`index_build`: input chains read of those stored, and whether reads are served from the previous index meanwhile), and the record of an index that replaced one from another schema (the reason, the previous and current schema identities, whether its build is still running), inputs waiting, chains behind their parse version, derived products pending, positions behind; what holds the writer and its last commit's age; idle, busy, stalled or halted per unit. A rate and an estimate are shown only while the rate is steady (within about 20% over the last few minutes), otherwise "rate varying".
3. **Archive:** the path; bytes of the segment log, each database and the embeddings store, logical and on disk; the mode (`standalone` or `primary`, with the primary section of [primary-mode.md](primary-mode.md)).
4. **Sources:** one line per origin and location with input and session counts, the last new input, and the location's state: present, missing (since when), unreadable (the error), `unrecognized` files (counted per root, directory pattern and extension; [capture.md](capture.md#every-file-in-one-class)), and for Claude Code a warning when its transcript cleanup period is short; for AI Studio, "not authorized" with `polylogue install drive` until the Drive sign-in is done.
5. **Problems**, each by name: chains that failed to parse, with path and reason; halted and stalled units; record types and field paths new since the previous parse version; models with no price; texts the embedder rejected; stored bytes whose hash did not match; archive permissions wider than 0700/0600; the capture items ([capture.md](capture.md#capture-status)): non-empty `unrecognized` classes, refusals, unwired hook events and origins silent beyond their usual gap; annotation conflicts ([annotations.md](annotations.md#current-revisions)); markup that failed to write and notes whose target is missing ([markup.md](markup.md)); operator-accepted claims whose check now fails ([annotations.md](annotations.md#checked-claims)); delivery outcomes and daemon live-event lines awaiting a write, with their errors (`pending_writes`, [deliveries](agent-context.md#deliveries), [live events](live-sessions.md#live-state)).
6. **Running and waiting:** how many sessions are running and how many wait on the operator, with the longest wait; the rows themselves are the shipped saved queries `running` and `waiting` ([saved-queries.md](saved-queries.md#shipped-saved-queries)).
7. **Quota:** `quota` holds each subscription limit's current window, from the snapshot: `measured` with its `used_percent`, when it was measured and its reset, or `not_measured` with the reason (`no_reading` within the window's length, `no_percent` when the newest reading gives a state but no percent, `window_reset` when the window of the newest reading has ended). The snapshot reads the newest reading of each limit within the longest window's length: the quota events of that span and the messages of the sessions active in it, newest first, stopping at a session once every limit of its tool has a reading at least as new as the session's last activity, so its cost follows recent use rather than the archive's size. Burn, forecasts and past windows are `| measure quota` ([measures.md#subscription-quota](measures.md#subscription-quota)).
8. **Vectors:** `status --vectors` explicitly counts stored vectors per embedding model, including distinct texts, chunks, dimensions and failures. A key that holds only refused texts (a provider that refused before its first vector told the dimensions) is listed with its failures and no dimensions. These exact counts read the vector store at idle priority, outside the short status deadline; an explicit caller deadline still applies. Ordinary status and `--line` do not recount it. The typed `vectors` field is present when requested and readable; `vectors_error` names a failed read, with a degraded answer. `status --verify` includes these counts too. They require no configured provider or model calls. Provider configuration, missing-text estimates and build costs belong to `polylogue embed`'s preview ([installing.md#embedding](installing.md#embedding)).
9. **Notices:** the count in the last day and the latest three.
10. **Watches and rules:** every enabled watch (a saved query saved with `--watch`) and signal rule, with its author and when it last fired. Rules written by anyone but the operator that he has not judged are marked; they are rows of the shipped saved query `review`, so `polylogue review pick judge accept` settles them ([judging.md](judging.md#verdicts-on-annotations)).
11. **Settings** written by anyone but the operator that he has not judged, the same way.
12. **Harnesses:** for each installed harness, whether its hooks and MCP entry are installed, and the last hook line and MCP call seen; per-event detail is `polylogue 'sessions | measure hooks'` ([installing.md#installing](installing.md#installing)).

**The view.** On the command line `status` prints a headline and a line of daemon facts (mode, pid, uptime, busy or idle, the archive), then sections. The headline is what the daemon is doing or what most needs attention: `blocked` with the error, `building the index, step 7 of 12`, the words of a reply without figures (`figures not read yet since the daemon started`, `figures not read yet since the new index was installed`), else the first note with how many more follow, else `up to date`. The sections are each left out when it has nothing to say: `ARCHIVE` (sessions, messages, tool calls, documents; inputs with their bytes decoded, which is what the inputs hold rather than what the segment log takes on disk, and revisions; vector counts when requested; while an index is rebuilt beside a readable one, a line saying the figures are the installed index's), `READING` (files read of those stored as a bar, the other parse states, and each freshness dimension in words) or, while an index is built, `INDEX` (below), then `PRIMARY`, `LAST CHECK` (the daemon's last look at its sources for new and changed files, left out while an index is built since it is from before the build), `RUNNING`, `NOTICES`, `RULES` (signal rules in force, refused rules and held signals), `PENDING`, `SOURCES` (from each machine's last full walk: when it was walked (and on which machine, where the archive holds several), then one line per watched root with the origins whose files it collected, its state (`present`, `absent`, `unavailable`, `incomplete` with how many paths could not be read), and its files collected, ignored by reason and unrecognized), `UNUSED` (the most frequent unread source field and how many others there are; `--json` lists the 20 most frequent, `unused_fields` counts them all), `THREADS` (below), `RECENT` (the daemon's latest five log records, warnings and errors marked, with how many earlier ones `--log` prints; while an index is built only warnings and errors, since `INDEX` shows the steps) and `NOTES` (the reasons the reply is degraded; while an index is built, `INDEX` says what that means and the note restating it is left out). Counts have thousands separators below a million, then two decimals with `M`; sizes are in binary units; times are local, the time of day for today and the date before. On a color terminal the headline's color gives the state (green up to date, yellow working or with notes, red blocked), the running step is bold, finished and coming steps and daemon facts are dimmed, and bars use eighth blocks; the plain style (no terminal, or `NO_COLOR`) has the same layout with `#` bars. Archived text is printed with its terminal controls escaped. Lines are cut to the terminal's width (100 columns off a terminal).

**Build progress.** While an index is built, `build_progress` reports why (`reason`: the index it replaces had other tables, another format version or no format identity; absent when there was no index), the steps `finished` (each with its `seconds` and its last `count`), the `current` step (since when, its `count` of `done` and, when known before the step ends, `total` (reading stored files counts the stored chains of formats with a reading, and their bytes, before it plans the first of them, so its share and estimate are of the whole build from the start; a counted chain it then cannot read is done when planning finds it), in `bytes`, `files`, `records`, `indexes` or `sessions`, its rate `per_second` over the last five minutes, and its estimate), the steps `to_come`, an earlier attempt that failed (`failed_attempt`: its step and error) until the build ends, the share of the last minute the database writer was busy and each parse worker's CPU seconds per minute. The steps are the ones the build runs and announces, in order: finding files and storing files (a new archive's first pass only), reading stored files, sorting texts, writing tables, indexing, assembling sessions (each session whose readings one file states, counted against every session a reading states less those joined later), indexing sessions (the session tables' indexes assembling does not fill as it writes), joining sessions across files (the sessions whose readings several files state or that copies name, with the events no session holds, counted against those sessions), finishing indexes, search index, installing; the same names appear in the daemon's log. A step that has nothing to do is passed over. The view's `INDEX` section says what is being built from how many stored bytes and why, that reads and searches answer `index building` until the index is installed (or use the previous index meanwhile), the current step's bar with its share and estimate, each finished step with its time and count, the current step with its count of its total, rate and estimate (or, with a zero rate, `no sessions done in the last 15m`), the steps to come, and the time for the whole build. Samples of the current step's count are taken as it is recorded, at most one per 10 seconds, kept for 15 minutes; a new step starts with none. A step's estimate (`eta_seconds`, shown as `about 26 min left`) is given only from at least a minute of samples with a positive rate whose two halves differ by no more than a fifth and a known total; otherwise the view says why (`rate varying`, `total known when the step ends`, `estimate after a minute of progress`). Steps to come have no rate until they run, so the whole job's estimate is given only once none is left to come; until then the view says the time is unknown.

**Threads.** `threads` lists each daemon thread that is doing something: its name, what it is doing, outermost first (`building the index` › `indexing sessions`, `answering a request` with the operation, `parsing a file` with its path), each with the seconds since it began, and the seconds since the thread last made progress (starting something counts, and so does each file, chain, build commit or batch of search texts). Under each thread are the SQL statements it has run for at least 3 seconds, with the connection (`writer`, `archive writer`, `reader`), the SQL and its running time; a thread running such a statement is listed even with no work recorded. All of it is kept in memory by the threads themselves and read without a reader or a lock on anything busy, so it answers while the writer is stuck. The view's `THREADS` section has a line per thread, named without its `polylogue-` prefix, with its work and the time of the innermost, `no progress for` after 10 seconds without progress and `stalled` after 10 minutes, and under it each statement, running time first. A statement that runs for a second or more is logged when it ends, with its time, full-scan steps, sorts, automatic-index rows, virtual machine steps and SQL.

**The daemon's log.** Every daemon log record goes to the journal with its priority and is kept in memory, the last 200. `recent_log` carries the last 20; `--log` returns every kept one, and the view prints them whole. A rate logged once a minute goes to the journal only.

**`--watch`** redraws the view every two seconds until interrupted, each frame a new request; the daemon keeps nothing between them. It needs a color terminal and cannot be combined with `--line`, `--verify` or `--json`; MCP and HTTP refuse it.

`--line` cannot be combined with `--vectors` or `--verify`. `--manifest` requires `--verify`. MCP and HTTP accept ordinary status and explicit vector counts, but refuse verification before reading stored bytes or creating a manifest.

**`--line`** prints one line for status bars, within its 30 ms budget and with no read at answer time: the headline's words, the running and waiting counts with the longest wait, and each measured subscription window grouped by tool (`up to date · 2 running · 1 waiting 7m · claude-code 5h 61% 7d 20%`). A window not measured is left out of the line; `--json` carries it with its reason.

**Figures.** Totals come from counters the writer keeps in the transaction of the rows they count, never from a recount. Whether the index has caught up comes the same way: the writer keeps each stored chain's parse state (no checkpoint, current, no parser, partial, behind) with the change that moves it, counted by origin and parse version, and a read applies the reading contracts to those counts. No read or commit walks every chain; a writer that stopped without closing recounts once at its next start. A figure not measured is never shown as zero, and a ratio with a zero denominator is not measured.

**Exit code.** `status`, with or without `--line` or `--json`, exits with its reply's code: 0 for a current reply, 5 when the reply is degraded (an index behind, a halted unit or a figure not measured), as every other command does ([interfaces.md](interfaces.md#exit-codes)).

**Edge cases.** A new archive's status is `up to date` once its first pass is installed, with zero counts and its sources watched. An archive whose index cannot be read answers degraded, with `totals_error` naming why. With the daemon down, the CLI prints one line naming the service to start and exits 6. A starting daemon makes the client wait within its deadline and say so. Status over HTTP and MCP carries no local paths in errors.

### Checking every stored byte

- **At read time,** every read of stored bytes checks the frame's hash; a mismatch fails that read with a named error (the segment, the extent and the citing input) and records a problem, which fires `stored bytes mismatch`.
- **On demand,** `polylogue status --verify` asks the daemon for a full check at idle priority, read-only, with progress in `status`: every segment frame against its hash (the one scan in common's [hashed-blobs](https://github.com/Sinity/polylogue-sinex-common/blob/master/crates/hashed-blobs/README.md)), every blob's catalog sizes against its stored descriptor, every extent cited by a row present in its blob, every chain's extents contiguous from its start and covering its longest revision, the kept counters (`input`, `revision`, stored bytes) equal to the rows they count, and page checksums and `quick_check` of each SQLite database. Its reply is the status block followed by the check's counts: inputs, revisions, extents, observations and blobs, inputs, revisions and bytes per input format, observations per class and revisions per way they were produced, and every problem by name; with problems the reply is `degraded` (exit 5). The check is returned in the status answer's `verification` field and changes no row. Only the command line offers `--verify`: the check reads the whole archive, which no agent call should start by the way.
- **Manifest.** `status --verify --manifest FILE` also reads every revision's bytes through its chain (each chain once) and writes one line per revision, `input<TAB>number<TAB>length<TAB>blake3`, ordered by input and then number, to a new file on the daemon's host; a relative path is the caller's. The file appears complete or not at all: when a revision cannot be read the check names it and writes no manifest. An existing file is never replaced. A manifest computed independently from another copy of the same inputs (an older archive, a backup) compares byte for byte.
- **Recovery** from a mismatch is a restore from backup ([installing.md#backup-and-restore](installing.md#backup-and-restore)).
- The check has no schedule; a drill or periodic check is something someone runs.

## Notices

Polylogue's signals use the common [signals](https://github.com/Sinity/polylogue-sinex-common/blob/master/crates/signals/README.md) rule schema, evaluator, interrupt budget and desktop notifications.

What is Polylogue's:
- **Storage.** A rule is an annotation of kind `signal` ([annotations.md#kinds](annotations.md#kinds)); each firing is a delivery naming the rule and revision, the triggering occurrences with their observation, the time, the channel, and the route decision with its holds and the attention it was decided under ([agent-context.md#deliveries](agent-context.md#deliveries)). Deliveries survive an index rebuild and reach Sinex in primary mode.
- **Rules.** `query` is a `query:<hash>` or saved name over Polylogue's catalog; `target` and `command` name entries of the deployment's signal configuration ([installing.md#configuration](installing.md#configuration)), so a rule can run only what the deployment configured; `scope` routes notices to the session-start brief of a repository or session. A rule is written with `note --as signal` on the selection whose question it watches (`polylogue query:waiting note '{"for":"20m","notify":true}' --as signal`), changed with `edit` and taken back with `withdraw`; every author may write, edit, enable and withdraw rules, and the author is computed.
- **A watch is a rule** with `fires: on_change` and `deliver: notice`, written by `save NAME --watch` (`polylogue 'tool_calls where outcome:error since:7d' save failing --watch`; [saved-queries.md](saved-queries.md#watches)); there is no second watch mechanism.
- **A page watch** is a watch named after its page, written by `polylogue page:flaky-ci save --watch` over what the page places ([pages.md](pages.md#time-and-checkpoints)). Its notices are those of any watch, and like every notice it never starts or resumes an agent.
- **Occurrences** follow lineage: for rows about sessions, the occurrence is the logical session ([sessions.md#logical-sessions](sessions.md#logical-sessions)), so a waiting episode carried across a fork, resume or continuation fires once. Repeats of the same note (same kind, target and value) are one occurrence.
- **Injected text** (`injected_context`) and deliveries are excluded from every rule's input.
- **Imports only:** a rule whose query reads only imported exports can fire no earlier than the next import, and writing it says so.
- **Incomplete:** a rule is `incomplete` while `status` does not say "up to date" for the data it reads.
- **Outlets:** `status` (count and latest), the next session-start brief whose scope the notice concerns, a desktop notification for interrupting notices, the change feed, and the shipped saved query `notices` (`polylogue notices`). Notices addressed to sessions reach them at their next context-accepting hook event ([session-control.md#notices-to-sessions](session-control.md#notices-to-sessions)).
- **One deliverer per host.** Standalone, Polylogue's daemon shows its own desktop notifications. In primary mode its evaluator sends its reports (firings, cleared conditions, rule revisions and progress) to Sinex, whose deliverer routes them under the one interrupt budget and quiet hours; Polylogue notifies directly only for `Sinex blocked`.
- **Value and action deliveries** run only targets and commands the deployment configured. No rule starts or resumes an agent session ([session-control.md](session-control.md#send)).

**What interrupts.** A notice interrupts only when the operator would want to stop what he is doing for it; everything else is passive (status, briefs, the feed). "Agent waiting on you" is passive unless the operator makes it interrupting.

**Shipped rules.** Shipped rules are data in the code, listed and read like authored rules, with no author record; they count as the operator's for the interrupt budget. An authored rule with the same name replaces the shipped one, withdrawing it brings the shipped one back, and disabling is an authored revision with `enabled: false`.

| Rule | Condition | Fires | Default channel |
|---|---|---|---|
| daemon stalled | a unit has work pending and no committed step | `on_new`, `for: 10m` | interrupting |
| source unreadable | a declared location cannot be read | `on_new`, `for: 1h` | interrupting |
| capture stalled | a watched input has appended bytes not committed | `on_new`, `for: 10m` | interrupting |
| Sinex blocked | primary mode: Sinex unreachable or refusing this producer | `on_new`, `for: 10m` | interrupting |
| agent waiting on you | a session in live state `waiting` | `on_new`, `for: 5m` | passive |
| unit halted | a unit entered its halt state | `on_new` | passive |
| stored bytes mismatch | a read or `status --verify` found a hash mismatch | `on_new` | passive |
| new parse failures | chains failing that did not fail at the previous parse version | `on_change` (`membership`) | passive |
| Claude Code cleanup short | Claude Code's transcript cleanup period would delete transcripts before collection | `on_new` | passive |
| brief lost | a prepared brief ended `not_sent` | `on_new` | passive, and to the session at its next hook |

Sinex's own notices are Sinex's and reach the operator through Sinex's deliverer; Polylogue does not repeat them. A refused archive (exit 78) and a dead process are reported by the service manager's failure notification.

## The change feed

`polylogue dev feed --after POSITION` is the position-based stream of changes programs read to stay current with an archive: the web's live views, the brief's scope index, outside mirrors. It sits under `dev` because no person types it as an everyday act ([interfaces.md#discipline](interfaces.md#discipline)).

- **One call is one finite batch** in the shared server-sent-event framing ([interfaces.md#operation-table](interfaces.md#operation-table)): a begin line, a record line per change, and a completion line with the new position and the count; the command line prints each as one JSON line.
- **A change is a reference and its write counter**, never content: on the archive side, annotations written or revised; on the index side, sessions whose rows or derived values changed and sessions no longer shown. The two sides are separate components, each in its own commit order, never one chronology.
- **The position** is an opaque string from the completion line. A program saves it only after applying the whole batch and passes it as `--after` next time; the first call omits `--after`. Record lines carry the previous completed position, so a program stopped mid-batch starts that batch again. A position ahead of the archive is refused (exit 2).
- **A full listing** comes when there is no position or the index was replaced since it was written: the begin line says `replacement: true`, the batch lists every current reference, and the program discards what it held.
- **Over HTTP** the feed resumes by position, not page cursor, and refuses token budgets and paging options; the web's stream uses the position as its event ID ([web.md](web.md#live-behaviour)).
- **As rows**, the same changes are the unit `feed` (`polylogue 'feed where kind:session'`), with filters, fields and pages; `changes` is the reading view of what a session changed ([reading.md](reading.md#views)).
