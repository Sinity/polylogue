# Archive

What Polylogue stores and how it reads it: stored inputs and their chains, why nothing is deleted, readings and covered chains, text, how stored formats evolve, parsers and their parse versions, independent goldens, field accounting, the data the trace view reads, and format drift. Where inputs come from is in [capture.md](capture.md); the parsed model the parsers produce is in [sessions.md](sessions.md). The three stores and the durability order are in [architecture.md](architecture.md#stores); the segment container that holds the bytes is the common [hashed-blobs](https://github.com/Sinity/polylogue-sinex-common/blob/master/crates/hashed-blobs/README.md) crate.

## Stored inputs

- **`input → chain → extent → blob`.** An *input* is one source object: a file, a capture log, a container member, or a row-dump stream. Each read of it that adds bytes extends its *chain*; a new chain starts only when the source holds a byte that differs from the stored byte at the same place. *Extents* name byte ranges in *blobs*. A chain only grows: a step's new bytes are placed at the chain's stored end, each revision of a chain is at least as long as the one before, and a stored extent never changes, so every revision reads back as it was stored. A step that would shorten its chain or place bytes over stored ones is refused.
- **Growth is a candidate for append.** Before reusing stored bytes for a mutable file, capture compares every byte of the proposed prefix with the stored chain. For a provider-named input this also applies to copies at other paths, including decoded copies. The inode, length, timestamps and a matching tail do not establish that the prefix stayed intact. When the prefix agrees, only the suffix is new archive data. A line input continues parsing at its committed record boundary.
- **A document its source saves whole is stored as chunks.** A document origin's file (an export, a JSON or Markdown document saved again) changes in place rather than growing, so a revision that changes it starts a new chain. Its bytes are cut into content-defined chunks (the common chunker's 16, 64 and 256 KiB minimum, target and maximum), each stored as a blob of its own, and the revision's chain has one extent per chunk in order. A revision that changes one place shares every other chunk with the revision before it, so only the chunks around the change are stored again. Bytes that make one chunk are one blob, as are appended bytes, imports (named by their whole bytes) and every other input. The bytes are cut the same way in both modes ([primary-mode.md](primary-mode.md#bytes)) and always read back exactly.
- **Blobs** are content-addressed and live in the shared segment log. A put appends them and syncs once for all the puts waiting together, then records their blob rows, with how far the segment is committed, before it returns; the extents that cite them commit afterwards with the input's rows. A blob put before a crash is found by the resumed write and not stored again; a tail no blob row names is cut when the segment opens. Appending checks the prepared length and encoded hash while it copies the bytes into the segment. The blob store is the stored record of every captured input, not a cache of bytes that still exist at the source, because tools prune and rewrite their own files.
- **An input is named as its origin declares.** A file a tool keeps at one place, matched by a declared [location](capture.md#roots-locations-and-the-ignored-list), is named by the first 32 hex digits of BLAKE3 of the machine name, a zero byte and the real path's bytes (its directory's symlinks resolved, so a file reached through a linked directory is one input), so a move or another machine makes another input. A file the tool moves or compresses itself is named by the *provider ID* written in it and the machine: a Codex rollout that names its session is `codex:rollout:<session id>@<machine>` wherever it lives on that machine and however it is compressed. An incomplete first record is retried as the file grows. A complete first record without a session ID is kept at its location with the parse refusal described in [Capture](capture.md). An imported file is named by its *content*, the full BLAKE3 hex of its bytes, and is recorded in one commit as one chain of those bytes, the same on every machine.
- **Every input has one writer.** An input is either tied to one machine (a location, a provider ID) or is its content, which is the same bytes wherever it is imported. No two machines ever write chains of one input, so a chain's number is its writer's own and chains are never renumbered ([primary-mode.md](primary-mode.md#several-machines)).
- **Observations** record each time an input was found at a location as the location changed: `first` (a location's first revision), `appended` (found grown at another location than the last), `rewritten`, `deleted`, `back` (seen again holding no byte its chain lacks: a stored revision, or fewer bytes of its chain, with the length seen) and `imported`. An append at the location the input was last observed at writes no observation: its revision records it, with when its bytes were read and the file's modification and change times then, which the next look at the file compares with. An observation names its location by the bytes read; the latest one is the one with the largest ID, which begins with the write counter. **A file that disappears is an observation, never a deletion.** A file that comes back, or is replaced at its path by another inode, continues its chain while every byte it holds equals the stored byte at the same place: the same bytes, or fewer, are observed `back` with the length seen; more bytes are appended; and only a byte that differs starts a new chain. A device number alone does not change a file's identity, because mounting assigns it (btrfs subvolumes, network and FUSE mounts).
- **Which chain of an input is newer is decided by the commit order of the machine that wrote it**, never wall-clock time. Chains are compared only within one input.
- **A new chain records where it stops agreeing with what came before.** With a new chain the record keeps the earlier chain of the same input that the new bytes begin like for longest (the newest of equals), and through which byte, as compared when the chain was stored. The value is fixed then and never changed. How far any two chains of an input are known to agree follows from these values without reading a byte: at least as far as the shortest agreement on the way from one to the other. The known agreement is never longer than the true one. It is recorded with the bytes so that no build compares bytes to find it ([Readings](#readings)).
- **Export containers are kept whole.** A ZIP or tar import stores the container exactly as given as one input and each member as its own input, addressed `container!/member`; identical member bytes are stored once with every observation kept. A repeated import at the same receiving location, with the same machine, author and member bytes, keeps its import namespace and adds no observation; a change to any of those establishes a new namespace.
- **Tool databases** are inputs of row dumps ([capture.md](capture.md#tool-databases)).
- **The archive is complete.** It holds every original input the user has. Inputs that only an earlier store still holds arrive as ordinary files through `import` ([capture.md](capture.md#import)); there is no reader for an earlier store ([Evolution](#evolution)).

## No deletion

Polylogue keeps every input and every reading of it; the deletion stance is stated in [architecture.md](architecture.md#deletion).
- **Re-parse is not deletion.** It replaces a chain's reading with a new reading of the same stored bytes, in one transaction.
- **Stored text is kept as written.** Polylogue stores and serves text like a text editor does, with no secret detection or masking. If a secret in history matters, the user (or an agent asked to) edits it out of the source file; both revisions of that file stay in the archive.
- A conversation that disappears upstream (absent from a complete newer export, deleted in Drive) is marked `source: gone` and keeps its rows. Deleted in Drive is what the newest chain of the Drive collector's listing states ([capture.md](capture.md#ai-studio-through-drive)). A complete export is one that lists every conversation of its account (ChatGPT, claude.ai and Grok exports): one input, or every input of its import. It is newer than a conversation when it holds a message later than the conversation's last activity, so the mark depends on the exports' contents, never on the order they were imported.

## Readings

A *reading* is what a parser, at its parse version, makes of one chain: one row for each session, message, event, link, document and alias the chain's records state. The index is built from readings and from nothing else ([architecture.md](architecture.md#pipeline)).

- **A reading is a function of its chain's bytes and its parser's parse version.** Reading the same bytes again changes nothing. What a parser makes of a record depends only on the bytes of its chain up to the end of that record, so two chains of one input that begin with the same bytes read alike over them: every record that ends within the shared bytes yields the same rows in both.
- **A reading is owned by its chain.** Its rows carry the input and the chain and belong to no other reading. A re-parse replaces that chain's reading whole; readings under older parse versions are not kept, because the bytes reproduce them.
- **A covered chain has no reading.** A chain is *covered* when a newer chain of its input is known to begin with all of its bytes: the same bytes, or its bytes followed by more. Everything a covered chain's records state, the newer chain's reading already holds at the same byte positions, so a second copy would say nothing.
- **A chain that only begins like a newer one reads its own part.** When a newer chain of the input agrees with it through some byte and then differs (a file rewritten with a shared beginning), its reading holds the rows of its records that end after that byte, and the rows before it are the newer chain's. A document read whole is one record, so an earlier revision of a document is covered by a revision with the same bytes and otherwise keeps its whole reading.
- **Nothing is dropped that a newer chain does not hold.** Covering is decided from the agreement the record keeps ([Stored inputs](#stored-inputs)), which is never longer than the true one. Where the record knows less than is true, an older chain keeps rows a newer one also has; they change nothing shown.
- **Which chain speaks for an input.** For each thing an input states, the input's reading of it is that of the newest of its chains whose reading holds it. So a natively named message that a rewrite dropped stays shown from the older chain that held it.
- **A rewrite shows only what it still holds, for content-named messages.** A message named by its content counts only from the newest chain of its input that has a reading: one that the newest chain no longer holds was deleted, or edited into a message with another ID, and stops being shown from that input.
- **Which chains held a record is read from the record.** A chain holds every record that ends within the bytes it is known to share with the chain whose reading has the row, and held it from the first of its revisions long enough to contain it. The trace view, a row's sources and the time a row was first seen are answered that way, for covered chains as for any other.
- **Every identity hash reads one JSON encoding**: the shared canonical JSON (a domain tag where the identity has one, object keys sorted, numbers as spelled), so no hash depends on map order or on the features serde_json was built with.
- **Times keep their source precision.** A parsed time keeps the precision, quality and bounds the source gave it ([capture.md](capture.md#source-clocks)); millisecond columns used by queries are an index over it and never replace it.
- **Message IDs are stable across re-parse and rewrite.** A message takes the source's own ID where the source gives one. A record without one (an AI Studio chunk, a Codex item, a Gemini page turn or activity entry, a Claude Code record without `uuid`, every Grok CLI and Aider message) is named by its content: its session, a hash of its role and content, and how many earlier messages of the session in the same chain had the same role and content (`<session>~<role>-<hash>-<n>`). A position is never part of an ID, because a rewrite moves positions; an edited message gets a new ID. An unchanged message keeps its ID unless an earlier message of its session with the same role and content was removed or inserted: equal messages are numbered in order, so removing an earlier copy gives each later copy the number one lower (`A X A` rewritten as `X A` gives the remaining `A` the first `A`'s ID). Equal messages say the same thing, so a note on the removed copy then names the copy that remains, and the former ID of the last copy reads as missing; nothing rewrites the note. The kind of ID is recorded with each reading's row (`id_kind`).
- **A stored row never reads as a default.** A stored name the model's enum does not have, an ID that does not parse, unparseable attributes or a negative count is a read error naming the row or column; it is never read as a user message, empty attributes or a skipped row.
- Which route's reading of a conversation is shown, field by field, is in [sessions.md](sessions.md#one-conversation-through-several-routes).

## Text

- **Each distinct text is stored once.** A text is the prose of a block, a tool's output, the body of a document. Its identity is BLAKE3 of its UTF-8 bytes. The index has one row for each distinct text and one copy of its bytes; message bodies, blocks and transcript entries hold the text's key and never its bytes. A message read through five routes, a prompt copied into fifty subagent files and a tool output a rewrite repeats each cost one copy.
- **Text is held in the index, not read back from the stored input.** A session can be read and searched when its bytes are not at hand (in primary mode, with Sinex unreachable), and reading does not depend on running a parser.
- **Texts read together are stored together.** A text's bytes are in a content group of texts ([Content](#content)): the texts of one reading one after another, up to about 64 KiB, or one longer text alone. The texts of one session lie together, and consecutive reads from one group decode it once. Bytes of a text that an earlier group already holds may stay in a later group beside new texts; they are never read.
- **Full text names a text by its key in this index; vectors name it by its hash.** There is one full-text entry for each distinct searchable text, and a hit reaches its messages through the blocks that hold the text ([search.md](search.md#index-maintenance)). A key a removed text had is never given to another text. Vectors are keyed by the text's hash and the model in `embeddings.db`, outside the index, so replacing the index never loses or recomputes a paid vector. Each text also records BLAKE3 of its NFC form for request lookup; several raw spellings may share it.
- **A text leaves with the last row that holds it**, together with its search entries, in the transaction that removes that row. Nothing is left for a later cleanup.

## Content

- **Each content is stored once.** A message reading's content is its fields, then each of its blocks with its text moved to its text row, and apart from each block its structured value (a tool result's data); an event reading's content is its fields, then its data. That content is stored once, in a content group, and nothing else in the index holds those bytes: the reading's row and the shown rows hold keys, times, hashes and small columns, and a reference to the piece. A shown block names the piece of its message's main reading that holds the block, and a shown event the piece of the reading it shows; the shown event's session and the message it follows are its own columns, since a copy's event is shown under the names its session gives.
- **Content is compressed in groups, in the order it was read.** A content group is one zstd frame of pieces laid one after another as a parse worker wrote them, up to about 64 KiB, or one longer piece alone; a group holds texts, or readings' content. A reference is the group, the start and the length in its decoded bytes, so neighbouring rows read from one decoded group, and a reading's content is read whole without its texts.
- **An opaque payload stays in the stored bytes.** A value no search, count or reading uses until it is shown, and that the input keeps byte for byte, is not copied into the index: a Codex reasoning item's encrypted content, and the history a Codex compaction restates. The parser names where it is (the record's byte range in its chain and the value's JSON pointer in the record), and the index holds that place in the value's stead. A read of whole values (an export, a message or event read as data) takes the value from the record; a text read shows that the reasoning is encrypted, or that a compaction restated history, without reading it. A message or event read while those bytes are not at hand still reads, with the value's place where the value would be; an export needs the bytes. A message's version is its content hash with the value in place, so it does not change with where the value is kept.
- **A group never changes and its key is never given to another group.** A group is named by the hash of its compressed bytes, so a group a later step or another build worker brings again with the same bytes is the same row. A group leaves, in the transaction that removed the last row naming it, once no text, message reading or event reading names it; the shown rows name only pieces of the readings present, so nothing else can.

## Evolution

- **No reader for an earlier store.** There are no importers for stores written by earlier builds of Polylogue or by Python Polylogue (except Python Polylogue's paid vectors, [capture.md](capture.md#import)), and no reader for an earlier version of any of Polylogue's own formats. History arrives as ordinary files, in each tool's own layout or as a Polylogue bundle, through the ordinary `import` ([capture.md](capture.md#import)).
- **One current format.** The record (`archive.db`) and the index are each created and opened only at their current format version, the same in both modes. `archive.db` names its archive by a random identity written when it is created (`meta.archive_id`). A format change edits the current schema, its writers and its readers together and regenerates test data; no conversion step is kept. A reading-version change re-parses exactly the chains it affects ([Parsing](#parsing)).
- **`embeddings.db` gains tables in place.** It holds paid vectors, so it is never set aside or rebuilt. Its schema is the vectors and failures tables followed by an ordered list of added tables (with their indexes and triggers); a schema change appends one to the list and never edits a released one. At open, a file whose tables, indexes and triggers are those of the base and an earlier part of that list gains the rest in one transaction; the `embedded` (vectors) table and its rows are never rewritten. Any other schema, a change to an existing table included, is refused (exit 78) with what differs from the nearest schema a build created, and the file is left as it was; such a change needs its own written plan.
- **An index from another build is replaced, never converted.** The daemon builds a new index from stored bytes in private files, reports the build in `status`, and installs it when the build ends ([installing.md](installing.md#replacing-an-index-from-another-schema)). `archive.db` in another format is refused with the version it found and left as it was.

## Parsing

### Parsers

- **One parser per origin, written from format knowledge.** Each parser carries the full knowledge of its origin's formats in every era (Claude Code todos, history and orchestration; Codex; Hermes; the Antigravity RPC; Gemini CLI sidecars; ChatGPT attachment resolution) and reads records as they are; there are no repair passes over parsed rows.
- **A malformed record is presumed to be Polylogue's bug.** It is counted per input with its reason, never skipped silently.
- **Origin, format, route and harness are separate coordinates.** A record's model field is trusted over the harness name: a DeepSeek model running under the Claude Code harness is DeepSeek.
- **Parsers are pure.** What a parser makes of a record depends on the bytes of its chain up to the end of that record and on nothing else: no stored state, no other input and no lookup in the index. What it carries from one record to the next is bounded by what is still open, never by how much it has read ([architecture.md](architecture.md#parsers)).
- **Rows name things as the source names them.** A parent, a tool call, a link's ends and a record that stands for another are written into rows by the names the source used, and are joined to what they name afterwards: within the chain when its reading is formed, within the session when it is composed, and across sessions when read ([sessions.md](sessions.md#names-and-references)). A parser never waits for, looks up or remembers the thing a record names.
- **Markup** (`::kind(args)` in transcripts) is extracted at parse time into annotations authored by the message's author, with IDs derived from the origin, message and marker line (never its position) so a re-parse writes the same annotations ([markup.md](markup.md)).

### Parse versions

- **Each parser module declares its parse version.** A chain is read again when the parse version of the module that parsed it changes or its stored bytes change, and nothing else triggers a re-parse: there is no index-wide version, and a new build of Polylogue with the same parse versions reads nothing again. A parser fix that changes what a chain yields raises that module's parse version.
- **An origin declares its parser modules once.** The origin's module macro requires each named module's `VERSION` and includes the shared record readers, message naming and export reader. Within a parser, the macro that declares child modules also collects their versions, recursively; each child must export `VERSION`. Origins without a parser use only the record readers and row-dump metadata parser, without message naming or export modules. Origin declaration values that classify messages have their own module version too. The parser version is the ordered list of those module names and versions; source bytes are never hashed. A test follows parser entry points, child declarations, public child calls and explicit `crate::` references and checks that every referenced parser module is included. The check does not follow the registry's references to other origins; changes in model types, external crates or indirect calls still require the author to raise the affected module's version.
- **A chain is in one of three states**, stored in one row of the index and read back as one value by every reader; one function, from that state and what the archive says of the chain (its stored length, whether a newer chain repeats it, its origin's parser version), answers whether it is due, and another how it is shown.

  | State | Meaning | Shown as |
  |---|---|---|
  | no reading | the chain has not been read, is covered ([Readings](#readings)), or its origin has no parser | `parsing` while it is due; `repeated`; `no_parser` |
  | complete at a length, under a parse version | the reading holds every complete record within that many bytes, and the state records the stored length the parser saw | `done`; `waiting` with the length, while a record is still being written past the last complete one; `parsing` while the chain is stored further than the length the parser saw |
  | failed at a parse version, with the reason | the parser could not go on at a record; the rows of the records before it are kept and the state names the place | `refused` when the input failed its origin's shape check; `failed` with the error otherwise |

- A chain is due exactly when its stored length differs from the length its state saw or its parser's version differs from its state's. A chain that grew past a complete state goes on from that state when the state keeps what the parser carries; otherwise it is read whole again. A failed chain is tried again when its stored bytes change or its parse version does, and at no other time: starting the daemon, a new build of Polylogue or another pass does not read it again. A failure to read the first bytes of an input that has no stored chain is a source error, retried on the next pass.
- **A part of a reading is refused unless it starts where the stored state ends.** A part planned from an earlier state (a read that was dropped, a plan made before another part committed) changes nothing and leaves the chain due from what is stored; it is never recorded as the chain's failure.
- A re-parse prepares the new reading aside and replaces the chain's reading in one transaction; other chains stay readable throughout. It reads the stored bytes and writes only the index.
- A chain that can still grow keeps the small state its parser needs to go on from its last complete record. Without it the chain is read from its start, which gives the same reading.
- An incomplete suffix waits at its recorded byte length. A finished input (an import, an export member) has none: the end of its bytes ends its last record, newline or not.
- A stored import whose recorded path no parser reads (or that recorded no path) is refused with that reason, and the pass goes on with the other inputs.
- Derivations carry their own versions ([measures.md](measures.md#rules)).

### Independent goldens

- **Expected outputs are written from format knowledge, independently of the parser, and never re-blessed.** No environment variable or command rewrites expected files from parser output; a golden changes only by an edit a reviewer reads.
- Each format era of each origin has goldens, as cases of input and expected outcome checked against the format knowledge.

### Field accounting and outcomes

- **Every leaf is accounted for, at any depth.** Each origin declares the paths it reads and the paths it keeps verbatim. Every leaf of a record, including leaves below a declared path, is one of: read into a column, kept verbatim in the row's attributes, or counted as `unused` with its full path. Declaring a parent path never hides its children.
- Fields that are read, not merely kept, include: Claude `thinking_tokens`, `server_tool_use`, `iterations`, every `tool_result` content part including `tool_reference`, `toolUseResult` for multi-result records, subagent messages present only inside `agent_progress`, signature-only thinking, exit codes, `structuredPatch` edits; Codex `base_instructions.text`, `git.commit_hash`, `originator`, `model_provider`, workspace roots, `context_window`, `agent_role` and `agent_path`, `phase`, `encrypted_content` as bytes, every `turn_context`; every column of Hermes `sessions`; ChatGPT citations, `content_references`, `search_result_groups`, canvas, search queries, selected sources, image results, async tasks, `weight`, inline cite marks; claude.ai `token_budget`, non-text tool results, per-block citations and timestamps, thinking summaries.
- **Record outcomes per input:** `used`, `skipped` (with a declared reason) and `unreadable` (with the reason). They sum to the records read.
- **Parse state per input chain** is the chain's state ([Parse versions](#parse-versions)): no reading, complete at a length, or failed with its reason. A failure is a fact of its chain; there is no separate failure table. Only the chain's bytes under its reading version fail it: a record the parser cannot read, counts that differ, decoded bytes that differ from their declared hash, a parser panic with its message and location, or an input its origin's shape check refuses. Anything else met while reading the chain (a busy database, an index replaced under a read, a part planned from an earlier state, a scratch file that cannot be written, a bug in the reading code) leaves the chain due and is read again; a build stops for a failure of the machine itself (permissions, a full disk) and is tried again.

Query records keep their source insertion position for incremental
readers. Older records whose position was never recorded keep an unknown
position; startup snapshots include them. This metadata does not change the
query's stored bytes, normal-form hash or saved dependencies.

## Trace data

The `trace` view ([reading.md](reading.md#trace)) reads three derived data sets. They live in `index.db`, follow the derivation rules of [measures.md](measures.md#rules) (stored at row or session grain, versioned, computed again by re-parse like every derived row) and are never sources of truth: the stored bytes are. Unknown stays unknown: where the records do not show an origin, the trace says so and names nothing.

- **Quote and paste origin index.** Each message's text is cut into overlapping windows, normalized (case, whitespace) and fingerprinted, stored with the message. A span's origin is the earliest message holding the same fingerprints, by source time with commit order breaking ties; every later occurrence is listed too, paged. A candidate is confirmed by comparing the text itself, so a fingerprint collision never names a false origin. The window length is the declared constant and is printed. Paste spans ([sessions.md](sessions.md#pastes)) are traced the same way, so a paste is traced to the message its text first appeared in.
- **File-line lineage.** Each edit call (a file write, an edit with its old and new text, an applied patch) stores the repository-relative path and the line ranges it replaced and wrote, from its arguments and diff. For `polylogue 'file:crates/store/src/writer.rs#L120' read --view trace`, the line is read from the repository's file, then the edits of that path are walked back in order, the line number mapped through each change, to the call whose written text is that line; the trace names the call, its session and its diff, and the earlier calls that touched the line. A line no captured edit wrote, or one changed since by something outside capture (a shell command, an editor, a checkout), is "not written in a captured session".
- **Record-to-bytes chain.** Every parsed row cites the input record it was read from: the input, chain and byte range, the stored blob holding those bytes ([Stored inputs](#stored-inputs)), and the parse version of the parser that read them ([Parse versions](#parse-versions)). The trace prints the chain record → input record → stored blob → reader version, and `read --view raw` shows the bytes.

## Format drift

Providers change their formats without notice. Drift is found by field accounting during parsing, not by inferring and committing schemas.

- **The walk.** The one full-depth walk per record that parsing already does accounts for every leaf. Origin declarations carry the expected type on each path a parser reads, explicit dynamic-key maps, and the known values of `type` fields.
- **The wire-shape tables.** Derived tables record, per format, record kind, path and type, when it was first and last seen and how often: `wire_shape` holds each reading's counts per path and `wire_type` per JSON type, as integers, and `wire_declaration` holds what a parse version declares about a path once per format. Every field declaration names its own record kind (or, for a declaration that lists the `type` values it reads, that value), and no two declarations of an origin share one, so a reading declares each kind and path once. Rows cite the source commits (where and when a shape was first and last seen) by number, and `wire_occurrence` holds each occurrence once per reading. Whether a path was present in a complete reading is read from the reading's completions, not stored on each path: a path counted now was present at the reading's latest completion when it was first seen before it, and a path a reset left uncounted was present at the completion before that reset when it was last seen before it.
- **The counts follow the reading.** A chain's counts are of the rows its reading holds: when the reading starts again from the chain's first byte, its counts start again with it, and a step the reading takes is never refused on account of its counts. Coverage includes the inspected length even when the last record is still incomplete. A completion records an actual complete read and can precede the current inspected length. A chain whose counts do not cover its reading from its first byte is partially covered, and a partially covered chain shows no field as having stopped appearing.
- **The `drift` measure** (`| measure drift`) shows new paths, type changes and fields that stopped appearing, per origin and parse version, newest first; status shows the same counts ([capture.md](capture.md#capture-status)). A database table no parser knows appears there too.
- **One shipped notice**, `format-drift`, is passive: it reaches the session-start brief of agents working in Polylogue's own repository ([operations.md](operations.md#notices)).
- **Acting on a drift notice:** compare the example input with an older one, write a golden for the new format, declare the field, and raise the parse version.

### Schema tools

The schema tools, `polylogue dev schema infer|unread|diff …`, describe the real shape of an origin's stored inputs without ingesting anything, for looking at a format by hand. They sit under `dev` because they are parser maintenance, not everyday acts ([interfaces.md#discipline](interfaces.md#discipline)). They run in the daemon at idle priority, read only stored bytes (never provider files), and write nothing into the archive or the repository. In primary mode they read the materials through Sinex.

| Command | Does |
|---|---|
| `dev schema infer [ORIGIN] [--input ID]… [--since TIME] [--revision N] [--field NAME]…` | the structure of the selected stored inputs (all of the origin's, or of every origin when no origin is named): field paths, types, presence and counts, streamed, with coverage (inputs and bytes read, what was unreadable) |
| `dev schema diff BEFORE AFTER` | added and removed paths, changed type sets, changed requiredness |
| `dev schema unread [ORIGIN]` | paths stored inputs carry that the parser neither reads nor declares kept, at any depth, for one origin or every origin |

- **No values.** Values never appear as examples, lists or enums. Object member names do, except identifier-shaped keys (UUIDs, long hexadecimal hashes, long numerals, dates and timestamps, paths), which are grouped under `*`, as are members of maps with many distinct sibling names. `--field NAME` keeps a name ungrouped.
- **Paths** start at the root and use `/` between components; `[]` is an array element and `*` an unnamed member; literal `~`, `/`, `*` and `[]` in names are escaped as `~0`, `~1`, `~2`, `~3`.
- **Counts per path:** `types` (values of each JSON type), `occurrences` (all values), `present` (parents with at least one value there), `parents` (eligible parents), `missing` (`parents - present`) and `required` (every eligible parent had it). These are observations of the sample, not a guarantee about future inputs.
- **Selection.** Inference reads each input's latest revision, or the exact `--revision N`, reporting an absent revision. `--input` makes the report a sample. `--since` selects by the time an input was received; inputs whose time is unknown are left out and counted. The reply groups schemas by origin and reports the inputs selected, the bytes stored and the bytes read.
- **Background work.** One inference runs at a time and gives way to other daemon requests. There is no per-input size cutoff and no default deadline; cancellation and an explicit `--deadline MS` apply.
- **Output.** CLI, MCP and HTTP send the same daemon requests. `--to FILE` writes in the CLI process, and `dev schema diff` reads those files locally.
- **A diff** reports each kind of change separately, root fields first and then each table by name, each ordered by path, and labels populations as incomparable when their origins, revisions or reads differ, while still showing what differs.
- Observation streams records and discards scalar bodies. Memory follows schema shape and nesting depth rather than record count or scalar length; deep JSON is read without a fixed depth cutoff. Malformed input, including an unfinished array or trailing content, is refused.
- Tool databases contribute their row dumps' column shapes and table structure, reported per table: the declared column types, nullability, primary key, hidden or generated columns and `WITHOUT ROWID` ([capture.md](capture.md#tool-databases)) separately from the JSON types observed in rows, with empty tables and never-filled columns listed. SQL text and default expressions stay out. Browser captures are Polylogue's own format and have no inferred schema.
