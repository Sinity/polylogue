# Archive

What Polylogue stores and how it reads it: stored inputs and their chains, why nothing is deleted, versioned rows, how stored formats evolve, parsers and their reading versions, independent goldens, field accounting, the data the trace view reads, and format drift. Where inputs come from is in [capture.md](capture.md); the parsed model the parsers produce is in [sessions.md](sessions.md). The three stores and the durability order are in [architecture.md](architecture.md#stores); the segment container that holds the bytes is the common [hashed-blobs](https://github.com/Sinity/polylogue-sinex-common/blob/master/crates/hashed-blobs/README.md) crate.

## Stored inputs

- **`input → chain → extent → blob`.** An *input* is one source object: a file, a capture log, a container member, or a row-dump stream. Each read of it that adds bytes extends its *chain* (a revision that appends to the previous one continues the chain; a rewritten file starts a new one). *Extents* name byte ranges in *blobs*.
- **A document its source saves whole is stored as chunks.** A document origin's file (an export, a JSON or Markdown document saved again) changes in place rather than growing, so each revision starts a new chain. Its bytes are cut into content-defined chunks (the common chunker's 16, 64 and 256 KiB minimum, target and maximum), each stored as a blob of its own, and the revision's chain has one extent per chunk in order. A revision that changes one place shares every other chunk with the revision before it, so only the chunks around the change are stored again. Bytes that make one chunk are one blob, as are appended bytes, imports (named by their whole bytes) and every other input. The same chunks go to Sinex in primary mode ([primary-mode.md](primary-mode.md)), so the bytes are stored the same way in both modes and always read back exactly.
- **Blobs** are content-addressed and live in the shared segment container: one sync per write group, extents committed in the same transaction as the rows that cite them, a torn tail truncated on open. Preparation hashes the encoded bytes as it writes them, without rereading its output just to compute that hash. Appending still checks the prepared length and encoded hash while it copies the bytes into the segment. The blob store is the stored record of every captured input, not a cache of bytes that still exist at the source, because tools prune and rewrite their own files.
- **An input is named as its origin declares.** A file a tool keeps at one place is a *location*: the first 32 hex digits of BLAKE3 of the machine name, a zero byte and the real path's bytes (its directory's symlinks resolved, so a file reached through a linked directory is one input), so a move or another machine makes another input. A file the tool moves or compresses itself is named by the *provider ID* written in it: a Codex rollout is `codex:rollout:<session id>` wherever it lives and however it is compressed, and is not stored until its first record names the session. An imported file is named by its *content*, the full BLAKE3 hex of its bytes, which is the same on every machine.
- **Observations** record each time an input was seen, with the machine and path, as one of `first`, `appended`, `rewritten`, `deleted`, `back` (seen again unchanged) and `imported`. **A file that disappears is an observation, never a deletion.** A file that comes back, or is replaced at its path by another inode, continues its chain while it still begins with every stored byte: the same bytes are observed `back`, more bytes are appended, and only changed stored bytes start a new chain. A device number alone does not change a file's identity, because mounting assigns it (btrfs subvolumes, network and FUSE mounts).
- **Which record is newer is decided by local commit order** (`commit_seq`), never wall-clock time.
- **Export containers are kept whole.** A ZIP or tar import stores the container exactly as given as one input and each member as its own input, addressed `container!/member`; identical member bytes are stored once with every observation kept. A repeated import at the same receiving location, with the same machine, author and member bytes, keeps its import namespace and adds no observation; a change to any of those establishes a new namespace.
- **Tool databases** are inputs of row dumps ([capture.md](capture.md#tool-databases)).
- **The archive is complete.** It holds every original input the user has, including Python Polylogue's hook spools, browser captures and their attachments, imported as declared older formats ([capture.md](capture.md#import)).

## No deletion

Polylogue keeps every input and every reading of it; the deletion stance is stated in [architecture.md](architecture.md#deletion).
- **Re-parse is not deletion.** It replaces a chain's parsed rows with a new reading of the same stored bytes: `retract(chain)`, then apply, in one transaction.
- **Stored text is kept as written.** Polylogue stores and serves text like a text editor does, with no secret detection or masking. If a secret in history matters, the user (or an agent asked to) edits it out of the source file; both revisions of that file stay in the archive.
- A conversation that disappears upstream (absent from a complete newer export, deleted in Drive) is marked `source: gone` and keeps its rows. A complete export is one that lists every conversation of its account (ChatGPT, claude.ai and Grok exports): one input, or every input of its import. It is newer than a conversation when it holds a message later than the conversation's last activity, so the mark depends on the exports' contents, never on the order they were imported.

## Versioned rows

Selected message metadata is prepared with the resolved message on the workers,
after source versions have been composed. This includes prose word counts,
serialized attributes and price estimates. The writer supplies row identities,
source coordinates and commit state, then stores the prepared metadata in the
same transaction as the selected blocks and parse position. Citation-only
updates keep using the existing selected row.

- **Each chain's reading of a row is stored**: one version per input chain, under the current reading version. A re-parse replaces that chain's version; readings under older reading versions are not kept, because the bytes reproduce them. The shown versions form a total order, and a growing file read again adds versions in commit order.
- **Reading the same bytes again changes nothing**: a row version's hash is a function of the bytes and the reading version, and a parse standing at a byte position depends only on the bytes before it. So an older chain whose bytes begin like a newer chain's of the same input has, at the end of its last complete record within the bytes they share, the reading the newer chain has at that point. A rebuild records the older chain's rows from the newer chain's reading there instead of parsing those bytes again, and the older chain parses only its own bytes after that point; a chain all of whose bytes the newer chain holds (the same bytes, or a prefix of them) is read to its end by the copy. A later record that changes an earlier row lies past that point, so the older chain keeps the rows it alone showed, and every chain a row appeared in stays recorded. A copy is taken while the newer chain's parse passes the point, which it stops at for the copy, or after the pass's parsing when the chains are identical or the newer chain is read as far as it will be. Shared bytes are decided by the bytes: extents taking the same blob bytes are alike without being read, and the rest is compared byte by byte, so a chain stored in other blobs (rewritten as one, or cut differently) shares its bytes too. A chain's bytes are compared with the next newer chain's at most once per pass: when it shares a different number of bytes with that chain than that chain shares with a later one, it shares the smaller number with the later one, and only where the two numbers are equal are the bytes after that point compared. Each older chain takes its reading from the newest chain holding all its bytes in the same blobs when there is one, else from the newer chain it shares the most bytes with (the newest of equals), among the chains that can still be at that point: chains not read yet and chains read no further. The end of a finished input (an import) ends its last record, which a longer chain reads as an incomplete one, so such an older chain parses its last bytes itself. Where an input's reading writes rows its chains share (a repository lookup, tool-database rows), its parser reads a document whole, or the newer chain stopped, the older chain is parsed whole. The newer chain's parse stops for a copy at the end of the last complete record within the shared bytes, so it reads no byte twice; where no record ends there, nothing is copied. A copied reading's wire-shape counts and parser checkpoint cite the newer chain's read ranges over the shared bytes, with their occurrences taken again for the older chain's own revisions. Each complete copied chain commits its rows, retaken source commits and parse checkpoint together before the next copy starts. Occurrences are retaken by their full typed key (input, chain, reading version and occurrence number); each occurrence update seeks that key rather than scanning the chain. A refusal or a copy error leaves no copied rows or write-counter change. A stop rolls back only the current copy; completed copies remain and the next pass selects only chains still behind. The engine checks queued requests between complete copies. One chain can still contain a large reading. A pass reports the chains it copied (`readings_copied`) and the bytes of theirs the copies read (`bytes_copied`) beside the bytes it parsed (`bytes_read`).
- **Build key lookups narrow disk searches with bounded samples.** Each sorted spill keeps evenly spaced full-key samples within the same fixed memory allowance as its merge buffers. Samples narrow the disk search without increasing each requested read; duplicate keys crossing sample boundaries keep every candidate. The stored row still decides whether a candidate matches, including after rollback or local-key reuse.
- **Foreign-key checks keep their lookup indexes during a first build.** Query-only indexes can wait for one final sorted build. Child lookups needed when a message or session leaves its selected reading remain indexed, including event placements and child links.
- **Repeated stated events keep their selected rows.** Adding a stated source still keeps its source and first commit and marks the session's derivations for refresh. If every selected event field, citation and placement is unchanged, the writer leaves its event row and session items untouched. A changed payload, citation, followed message or position still updates the selected row and its items in the same transaction. Stored event entries and their fingerprints share one construction, including typed context-boundary data. An incoming event also checks its stored item fingerprint: old item metadata is rebuilt through the usual item rewrite and cursor invalidation, without reparsing source bytes.
- **A version leaves with its last reference.** Version bodies, event and link values and texts are shared between chains and rows; the transaction that removes the last source row, block or kept parser context referring to one deletes it, with its search entries, before it commits. Cleanup checks the removed-reference candidates through keyed lookups, so unrelated stored text does not add work to each transaction. Nothing is left for a later cleanup, and no search index needs a merge pass after a re-parse.
- **Every identity hash reads one JSON encoding**: the shared canonical JSON (a domain tag where the identity has one, object keys sorted, numbers as spelled), so no hash depends on map order or on the features serde_json was built with.
- **Times keep their source precision.** A parsed time keeps the precision, quality and bounds the source gave it ([capture.md](capture.md#source-clocks)); millisecond columns used by queries are an index over it and never replace it.
- **Message IDs are stable across re-parse and rewrite.** A message takes the source's own ID where the source gives one. A record without one (an AI Studio chunk, a Codex item, a Gemini page turn or activity entry, a Claude Code record without `uuid`, every Grok CLI and Aider message) is named by its content: its session, a hash of its role and content, and how many earlier messages of the session had the same role and content (`<session>~<role>-<hash>-<n>`). A position is never part of an ID, because a rewrite moves positions; an edited message gets a new ID. An unchanged message keeps its ID unless an earlier message of its session with the same role and content was removed or inserted: equal messages are numbered in order, so removing an earlier copy gives each later copy the number one lower (`A X A` rewritten as `X A` gives the remaining `A` the first `A`'s ID). Equal messages say the same thing, so a note on the removed copy then names the copy that remains, and the former ID of the last copy reads as missing; nothing rewrites the note. The kind of ID is recorded with each source row (`id_kind`).
- **A rewrite shows only what it still holds, for content-named messages.** Once an input's latest chain is read to its end, a message named by its content that the chain no longer holds stops being shown from that input (it was deleted, or edited into a message with another ID). A natively named message the rewrite dropped stays shown from the older chain that held it.
- **A stored row never reads as a default.** A stored name the model's enum does not have, an ID that does not parse, unparseable attributes or a negative count is a read error naming the row or column; it is never read as a user message, empty attributes or a skipped row.
- Which route's reading of a conversation is shown, field by field, is in [sessions.md](sessions.md#one-conversation-through-several-routes).

## Evolution

- **An archive from before the baseline is an input.** A database without Polylogue's format identity (`application_id` "PLG1") was written by an earlier Polylogue. It is a declared older input format, imported once into a fresh archive with `polylogue import PATH` ([capture.md](capture.md#an-archive-from-before-the-baseline)), never migrated in place.
- **One current format.** The register (`archive.db`), standalone index and primary cache are each created and opened only at their current format version. A format change edits the current schema, its writers and its readers together and regenerates test data; no conversion step and no reader for an earlier version is kept. A reading-version change re-parses exactly the chains it affects ([Parsing](#parsing)).
- **Parsed rows refer to message versions by a narrow key.** Each stored message version has an integer key that source memberships, layouts, shared text, attachments and parser context refer to. The full content hash stays in the version's metadata row and is translated at read and export boundaries; compressed bodies are kept in a separate one-to-one payload table. Each text row also records BLAKE3 of its NFC UTF-8 for request lookup beside the BLAKE3 of its raw UTF-8, which stays its identity; several raw spellings may share the normalized identity. During a build, stored-message validation uses the row key already held by a source or parser context, or the bounded build key map; it still checks the canonical body and full content hash. It does not rediscover that row through a deferred hash index. Local keys never enter citations or portable records. Removing the final source or parser-context reference deletes metadata, payload and child rows in the same transaction.
- **Text bodies are compressed in groups.** A distinct text is one `text` row (its hashes, search membership, and its place in a group); its bytes are in a `text_group` row, one zstd frame holding the UTF-8 of up to about 64 KiB of texts one after another, or one longer text alone. The parse worker that read the texts groups and compresses them in reading order, so texts of one session share groups; the writer stores a group in the transaction that first writes one of its texts and copies its bytes unchanged. Reading a text decodes its group, and consecutive reads from one group decode it once. A group leaves in the transaction that removes its last text; until then the bytes of its removed texts stay in it. A step's texts already in the index get no new row, but their bytes stay in that step's groups when a group has new texts too; on a sample of real transcripts such repeated bytes were about 2% of the text. Groups use zstd level 3; their compression work stays on the parse workers. Reading one text decodes its group, with a single text larger than the group size stored alone.
- **`embeddings.db` gains tables in place.** It holds paid vectors, so it is never set aside or rebuilt. Its schema is the vectors and failures tables followed by an ordered list of added tables (with their indexes and triggers); a schema change appends one to the list and never edits a released one. At open, a file whose tables, indexes and triggers are those of the base and an earlier part of that list gains the rest in one transaction; the vectors table and its rows are never rewritten. Any other schema, a change to an existing table included, is refused (exit 78) with what differs from the nearest schema a build created, and the file is left as it was; such a change needs its own written plan.
- **An index from another schema is replaced, never converted.** The daemon moves it into the build directory as the previous index, builds a new index from stored bytes in a private file, reports the rebuild in `status`, installs the new index when its build ends and then removes the previous one ([installing.md](installing.md#replacing-an-index-from-another-schema)). `archive.db` in another format is refused with the version it found and left as it was.

## Parsing

### Parsers

- **One parser per origin, written from format knowledge.** Each parser carries the full knowledge of its origin's formats in every era (Claude Code todos, history and orchestration; Codex; Hermes; the Antigravity RPC; Gemini CLI sidecars; ChatGPT attachment resolution) and reads records as they are; there are no repair passes over parsed rows.
- **A malformed record is presumed to be Polylogue's bug.** It is counted per input with its reason, never skipped silently.
- **Origin, format, route and harness are separate coordinates.** A record's model field is trusted over the harness name: a DeepSeek model running under the Claude Code harness is DeepSeek.
- **Markup** (`::kind(args)` in transcripts) is extracted at parse time into annotations authored by the message's author, with IDs derived from the message and position so a re-parse writes the same annotations ([markup.md](markup.md)).

### Reading versions

- **Each parser module declares its reading version.** A chain is re-parsed when the reading version of the module that parsed it changes, and nothing else triggers a re-parse; there is no index-wide version that rebuilds everything.
- A re-parse prepares the new reading aside, then retracts and replaces one chain in one transaction; other chains stay readable throughout. A standalone reading of stored bytes checks its recorded chain and logical length, then writes only the index; it does not register the input again or advance the archive counter. New decoded bodies are still stored as blobs before their reading can commit or be cancelled.
- An incomplete suffix waits at its recorded byte length. A finished input (an import, an export member) has none: the end of its bytes ends its last record, newline or not.
- A stored import whose recorded path no parser reads (or that recorded no path) is refused with that reason in its parse state, and the pass goes on with the other inputs. A refusal or failure also records the executable digest and any parser settings that affected the attempt. Current parsers expose no configurable parser settings, so their attempts have no settings digest. It stays stopped across restarts while that identity, its input chain, stored length and reading version match. Changed bytes, a new reading version or changed parsing dependencies make it eligible again. A newly eligible stopped attempt replaces its reading from the stored bytes, including when its failed cursor has no parser continuation. An older failure without an attempt identity is unrecorded: its next real attempt records the identity. A first-byte capture-read failure without a stored chain remains retryable.
- Derivations carry their own versions ([measures.md](measures.md#rules)).

### Independent goldens

- **Expected outputs are written from format knowledge, independently of the parser, and never re-blessed.** No environment variable or command rewrites expected files from parser output; a golden changes only by an edit a reviewer reads.
- Each format era of each origin has goldens, as cases of input and expected outcome checked against the format knowledge.

### Field accounting and outcomes

- **Every leaf is accounted for, at any depth.** Each origin declares the paths it reads and the paths it keeps verbatim. Every leaf of a record, including leaves below a declared path, is one of: read into a column, kept verbatim in the row's attributes, or counted as `unused` with its full path. Declaring a parent path never hides its children.
- Fields that are read, not merely kept, include: Claude `thinking_tokens`, `server_tool_use`, `iterations`, every `tool_result` content part including `tool_reference`, `toolUseResult` for multi-result records, subagent messages present only inside `agent_progress`, signature-only thinking, exit codes, `structuredPatch` edits; Codex `base_instructions.text`, `git.commit_hash`, `originator`, `model_provider`, workspace roots, `context_window`, `agent_role` and `agent_path`, `phase`, `encrypted_content` as bytes, every `turn_context`; every column of Hermes `sessions`; ChatGPT citations, `content_references`, `search_result_groups`, canvas, search queries, selected sources, image results, async tasks, `weight`, inline cite marks; claude.ai `token_budget`, non-text tool results, per-block citations and timestamps, thinking summaries.
- **Record outcomes per input:** `used`, `skipped` (with a declared reason) and `unreadable` (with the reason). They sum to the records read.
- **Parse state per input chain:** parsed, as `parsing` (stored bytes remain), `waiting` (with the stored length it waits at, while a record is still being written) or `done`; `partial`; `refused` (with the reason); `no_parser_yet`; `failed` (with the error). A failure is a parse-state fact of its input; there is no separate failure table. A refused or failed chain records the stored length and stopped attempt it was read at; the dependency rule above governs its next attempt. Successful progress clears the stopped attempt. The executable digest is computed once at the process boundary when a command starts an Engine; offline completion and read-only clients do not hash the executable.

Query records keep their source insertion position for incremental
readers. Older records whose position was never recorded keep an unknown
position; startup snapshots include them. This metadata does not change the
query's stored bytes, normal-form hash or saved dependencies.

### Keyed continuation

Claude response keys and record UUID aliases remain addressable for the whole input chain. Small in-memory windows cache them; Store keeps compact mappings and reuses the existing message versions. The mappings and the parser checkpoint commit in the same transaction. Each key keeps only its value at the chain's latest checkpoint: a response key holds its message version's local key and byte range, an alias its target message ID. The chain's context state names its reading version and checkpoint once; a reading from byte zero replaces the chain's whole context, and an extension applies only on top of a state of its own reading version. A resumed parse reads the context under the snapshot it opened at that checkpoint, so a value a later checkpoint replaces is never read again: the replacing transaction overwrites it, and a message version only it kept leaves with it. A replacement keeps one private context across its staged chunks, emitting only each chunk's changed mappings. Its committed lookup cutoff stays fixed while its private cursor advances. An attempt starting at byte zero uses only its private replay and holds no committed-index connection or read snapshot, even when its chain is already known. A resumed attempt keeps its selected committed snapshot until the attempt ends. A rejected preparation reports its original error in the pass summary and leaves the committed checkpoint, context and rows unchanged. If its failed cursor, chain, reading version and stored length exactly match an already committed stop, that stop keeps its original error and binds the retry's executable identity through the same progress path. Other rejected replacements remain eligible for a later attempt.

Response-version references keep their reverse index during first build and
parsing. Collecting a candidate version checks its references instead
of scanning kept context.

A new reading version reconstructs missing historical context from stored bytes through a re-parse. Once recorded, a restart resumes directly at that checkpoint. Lost derived context can be rebuilt from the committed prefix. An absent context record means unrecorded context, not a complete empty map.

## Trace data

The `trace` view ([reading.md](reading.md#trace)) reads three derived data sets. They live in `index.db`, follow the derivation rules of [measures.md](measures.md#rules) (stored at row or session grain, versioned, rebuilt by re-parse like every derived row) and are never sources of truth: the stored bytes are. Unknown stays unknown: where the records do not show an origin, the trace says so and names nothing.

- **Quote and paste origin index.** Each message's text is cut into overlapping windows, normalized (case, whitespace) and fingerprinted, stored with the message. A span's origin is the earliest message holding the same fingerprints, by source time with commit order breaking ties; every later occurrence is listed too, paged. A candidate is confirmed by comparing the text itself, so a fingerprint collision never names a false origin. The window length is the declared constant and is printed. Paste spans ([sessions.md](sessions.md#pastes)) are traced the same way, so a paste is traced to the message its text first appeared in.
- **File-line lineage.** Each edit call (a file write, an edit with its old and new text, an applied patch) stores the repository-relative path and the line ranges it replaced and wrote, from its arguments and diff. For `polylogue 'file:crates/store/src/writer.rs#L120' read --view trace`, the line is read from the repository's file, then the edits of that path are walked back in order, the line number mapped through each change, to the call whose written text is that line; the trace names the call, its session and its diff, and the earlier calls that touched the line. A line no captured edit wrote, or one changed since by something outside capture (a shell command, an editor, a checkout), is "not written in a captured session".
- **Record-to-bytes chain.** Every parsed row cites the input record it was read from: the input, chain and byte range, the stored blob holding those bytes ([Stored inputs](#stored-inputs)), and the reading version of the parser that read them ([Reading versions](#reading-versions)). The trace prints the chain record → input record → stored blob → reader version, and `read --view raw` shows the bytes.

## Format drift

Providers change their formats without notice. Drift is found by field accounting during parsing, not by inferring and committing schemas.

- **The walk.** The one full-depth walk per record that parsing already does accounts for every leaf. Origin declarations carry the expected type on each path a parser reads, explicit dynamic-key maps, and the known values of `type` fields.
- **The wire-shape tables.** Derived tables record, per format, record kind, path and type, when it was first and last seen and how often: `wire_shape` holds each reading's counts per path and `wire_type` per JSON type, as integers, and `wire_declaration` holds what a reading version declares about a path once per format. Every field declaration names its own record kind (or, for a declaration that lists the `type` values it reads, that value), and no two declarations of an origin share one, so a reading declares each kind and path once. Rows cite the source commits (where and when a shape was first and last seen) by number, and `wire_occurrence` holds each occurrence once per reading. Whether a path was present in a complete reading is read from the reading's completions, not stored on each path: a path counted now was present at the reading's latest completion when it was first seen before it, and a path a reset left uncounted was present at the completion before that reset when it was last seen before it.
- **The `drift` query unit** shows new paths, type changes and fields that stopped appearing, per origin and reading version, newest first; status shows the same counts ([capture.md](capture.md#capture-status)). A database table no parser knows appears there too.
- **One shipped notice**, `format-drift`, is passive: it reaches the session-start brief of agents working in Polylogue's own repository ([operations.md](operations.md#notices)).
- **Acting on a drift notice:** compare the example input with an older one, write a golden for the new format, declare the field, and raise the reading version.

### Schema tools

The schema tools, `polylogue dev schema infer|unread|diff …`, describe the real shape of an origin's stored inputs without ingesting anything, for looking at a format by hand. They sit under `dev` because they are parser maintenance, not everyday acts ([interfaces.md#discipline](interfaces.md#discipline)). They run in the daemon at idle priority, read only stored bytes (never provider files), and write nothing into the archive or the repository. In primary mode they read the materials through Sinex.

| Command | Does |
|---|---|
| `dev schema infer [ORIGIN] [--input ID]… [--since TIME] [--revision N] [--field NAME]…` | the structure of the selected stored inputs (all of the origin's, or of every origin when no origin is named): field paths, types, presence and counts, streamed, with coverage (inputs and bytes read, what was unreadable) |
| `dev schema diff BEFORE AFTER` | added and removed paths, changed type sets, changed requiredness |
| `dev schema unread [ORIGIN]` | paths stored inputs carry that the parser neither reads nor declares kept, at any depth, for one origin or every origin |

- **No values.** Values never appear as examples, lists or enums. Object member names do, except identifier-shaped keys (UUIDs, long hexadecimal hashes, long numerals, dates and timestamps, paths), which are grouped under `*`, as are members of maps with many distinct sibling names. `--field NAME` keeps a name ungrouped.
- **Paths** start at the root and use `/` between components; `[]` is an array element and `*` an unnamed member; literal `~`, `/`, `*` and `[]` in names are escaped as `~0`, `~1`, `~2`, `~3`.
- **Counts per path:** `types` (values of each JSON type), `occurrences` (all values), `present` (parents with at least one value there), `parents` (eligible parents), `missing` (`parents - present`) and `required` (every eligible parent had it). These are observations of the sample, not a guarantee about future inputs.
- **Selection.** Inference reads each input's latest revision, or the exact `--revision N`, reporting an absent revision. `--input` makes the report a sample. `--since` selects by the time an input was received; inputs whose time is unknown are left out and counted. The reply groups schemas by origin and reports the inputs selected, the bytes stored and the bytes read.
- **Background work.** One inference runs at a time and gives way to other daemon requests. There is no per-input size cutoff and no default deadline; cancellation and an explicit `--deadline MS` apply.
- **Output.** CLI, MCP and HTTP send the same daemon requests. `--to FILE` writes in the CLI process, and `dev schema diff` reads those files locally.
- **A diff** reports each kind of change separately, ordered by path, and labels populations as incomparable when their origins, revisions or reads differ, while still showing what differs.
- Observation streams records and discards scalar bodies. Memory follows schema shape and nesting depth rather than record count or scalar length; deep JSON is read without a fixed depth cutoff. Malformed input, including an unfinished array or trailing content, is refused.
- Tool databases contribute their row dumps' column shapes and table structure, reported per table: the declared column types, nullability, primary key, hidden or generated columns and `WITHOUT ROWID` ([capture.md](capture.md#tool-databases)) separately from the JSON types observed in rows, with empty tables and never-filled columns listed. SQL text and default expressions stay out. Browser captures are Polylogue's own format and have no inferred schema.
